## 2. 方法：为什么这些异常可以在 PC 侧注入

| 异常 | 怎么注入 | 是否需要改线 |
|---|---|---|
| CRC 错误 | 合法帧头 + 错误 CRC | 否 |
| 长度非法 | `LEN = 41 / 255 / 200` | 否 |
| 半截帧 | 发帧头 + 部分载荷后静默 | 否 |
| 未知命令 | `TYPE = 0x99` | 否 |
| 超长文本 | 200 字符一行 | 否 |
| TX 队列满 | 连发 100 条 `stat` | 否 |
| **帧错误 FE/NE** | **用 9600 波特率发数据**（与设备的 115200 不匹配，必然产生帧错误） | **否** |
| ORE | 需要 RX 在 DMA 未取走时又收到字节；正常接线难以制造 | 需电气注入 |

用"错误波特率"这一招很关键：它让设备收到大量畸形帧，触发**同一条** `HAL_UART_ErrorCallback` 路径，
却完全不碰硬件接线，也没有短路风险。

## 3. 逐项结果

### 3.1 CRC 错误 ×20

```
frame_err +20，uart_err +0，链路存活（ping 有 ACK / stat 有回）
```

每条坏帧都被计入 `frm`，解析器逐次复位，20 次全部不影响后续通信。
这正是"CRC 只发现内容损坏、不阻塞链路"的设计目标。

### 3.2 长度非法

```
LEN = 41 / 255 / 200 → frame_err +3
```

`PROTO_P_LEN` 状态一看到 `> PROTO_MAX_PAYLOAD(40)` 就回 `SOF0`，
三个非法长度全部被拒，没有出现"按 255 字节去写缓冲"的越界。

### 3.3 半截帧：确定性地吃掉后续 2 帧

先发一个"声称还有 10 字节载荷"的帧，只给 3 字节，静默 120 ms，再每 120 ms 发一个 ping：

```
ping #1 -> 丢失
ping #2 -> 丢失
ping #3 -> ACK
ping #4 -> ACK
ping #5 -> ACK
ping #6 -> ACK
结果：4/6 成功，前 2 个丢失
```

**这不是随机现象，而是可以精确推算的**：

| 步骤 | 消耗 |
|---|---|
| 半截帧停在 BODY 状态，还差 7 字节载荷 | 需要 7 B |
| ping #1（7 B）整帧被当作载荷吞掉 | −1 帧 |
| 进入 CRC 阶段，吃掉 ping #2 的 2 字节做 CRC，校验失败 → 复位 | −1 帧 |
| 剩余字节回到 SOF0，从 ping #3 开始正常 | 恢复 |

后果不止丢帧：**在这段时间里，文本通道也被吞掉**——因为 parser 不在 idle 状态，
`stat` 的响应字节被当作载荷消费，所以脚本里 T3 的 `after = link.stat()` 直接返回 `None`。

**严重度评估：低。** 触发条件是 PC 侧发出半截帧（程序中途被杀、USB 拔出、线路干扰落在帧中间）。
影响范围是"下一个命令丢 2 次"，用户再点一次就好。但如果要更稳，可以加空闲超时复位（见 §5）。

### 3.4 未知命令与非法文本

| 用例 | 结果 |
|---|---|
| 二进制 `TYPE=0x99` | 回 `ACK`，`result=2`（未知命令），`cmd_err +1` |
| 文本 `bogus\r\n` | 回 1 行 `ERR unknown command: bogus`，`cmd_err` 增量 **0**（文本命令不计入二进制命令统计，属设计） |
| 文本 200 字符 | 回显长度 **84 = 21 + 63**，被 `APP_LINE_BUF_SIZE-1` 截断，无越界，链路存活 |

### 3.5 TX 队列灌满（整帧原子性）

连发 100 条 `stat`（请求约 600 B，回显远超 1024 B 队列）：

```
收到 STAT 帧 14，SAMPLE 帧 201，txd 丢弃 +11333 字节
解析错误 0        ← 关键
链路存活（之后 stat 正常）
```

两个结论：

1. **丢弃是"整帧"的**：`app_tx_write` 空间不足时整包丢弃、计入 `txd`，
   所以线上**没有半截帧**——201 个 SAMPLE 帧全部 CRC 正确、解析错误 0。
2. 队列只有 1024 B，一次灌 100 条 stat 必然溢出，这是设计预期（正常使用每秒 1 条 stat，
   占用不到 200 B/s）。`txd` 字段让"丢了多少"可观测，不是静默丢弃。

### 3.6 HT / TC / IDLE：跨 64 字节 DMA 缓冲不重复不丢

`APP_RX_DMA_BUF_LEN = 64`，所以连续流一定会跨过 TC（缓冲满）事件。背靠背发 20 个 ping：

```
B) 20 个 ping = 140 字节（跨 64 边界 2 次）→ ACK 20/20，解析错误 0
C)  8 个 ping =  56 字节（不跨界，作对照）→ ACK  8/8，解析错误 0
```

**跨界组与不跨界组结果完全一致** → `Usart` 的 TC 分支（`Size=64` 上交 + 重挂）没有重复上交，
也没有丢字节。HT 分支的早退已在 v5.1.5 用反向对照验证过（去掉早退 → `rxf` +10、回显 84 字节）。

### 3.7 FE/NE 风暴与恢复（ORE 的替代验证）

```
用 9600 波特率发 32 字节 → 设备按 115200 采样，必然产生大量帧错误
uart_err +144，rxf +0，恢复后 ping/stat 全部正常
```

`rxf +0` 是这一项最有价值的数字：**144 次错误回调里，没有一次重新挂接收失败**。
说明 `HAL_UART_ErrorCallback` 里"先 abort、再清 ORE、再 `usart_start_rx()`"的顺序是对的。

> **为什么这不能算 ORE 验证**：ORE 是"上字节未被取走就来了新字节"，触发条件不同。
> 本次的畸形帧主要产生 FE/NE。二者共用同一个回调，但 ORE 分支还多一步
> `__HAL_UART_CLEAR_OREFLAG`。要真验 ORE，需要带电把 RX 短接到 GND（串 100 Ω）——
> 这是唯一有电气风险的一项，留到你确认后再做。

### 3.8 异常后的链路存活

每一项结束后都做了一次"存活探针"（发 ping 看 ACK + 发 stat 看回显）：

| 用例 | 存活 |
|---|---|
| CRC ×20 之后 | ✅ |
| 长度非法 ×3 之后 | ✅ |
| 半截帧之后 | ✅（代价 2 帧） |
| 未知命令之后 | ✅ |
| 超长文本之后 | ✅ |
| 190 B 连续流之后 | ✅ |
| 队列灌满之后 | ✅ |
| FE 风暴之后 | ✅ |

## 4. 由数据得出的两个判断

### 4.1 `s_rx_fail` 没有重试机制（潜在缺口）

`usart_start_rx()` 只在两个地方被调用：接收事件回调、错误回调。**一旦某次返回非 OK，
就只把 `s_rx_fail++`，没有任何重试**。后果是：

> 如果那一天真失败了，接收永久停摆，而设备看起来还在正常发 SAMPLE（TX 不受影响），
> 上位机能画曲线却再也收不到命令响应 —— 这是最容易被误判成"上位机卡了"的故障。

本次 144 次错误回调里 `rxf` 都是 0，说明没触发。但这是"没遇到"，不是"不会发生"。
低成本加固：主循环里检测 `usart_rx_fail_count()` 增长 → 限速 1 s 重挂一次。
与阶段一 ADC 恢复的做法对称。

### 4.2 RX 环形缓冲 256 B 无法自然溢出

115200 下 256 B 需要 22 ms 才能填满，而主循环每轮都把 `app_cmd_poll()` 的
`while` 循环跑到空（不是每轮只取一个字节）。所以除非主循环被阻塞 >22 ms，
否则溢出不发生。本次 190 B 连续流 `rxf` 增量为 0，符合这个推算。

**结论**：保护代码存在（`s_rx_ovf++` 后丢弃新字节，不覆盖未解析数据），
但"是否真的按预期工作"没有被实测覆盖。要验证只能用代码桩（人为阻塞主循环），
按你的规则我不擅自加。

| 现象 | 含义 |
|---|---|
