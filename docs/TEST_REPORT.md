### 7.2 本轮真正修掉的四个缺陷

| # | 缺陷 | 现象（存在该缺陷时） | 根因 | HAL / 代码证据 | 修法 | 强度 |
|---|---|---|---|---|---|---|
| 1 | **HT 回调重复上交** | 一次 IDLE 收到的字节被上交两次；回调里重挂接收直接拿到 `HAL_BUSY` | `HAL_UARTEx_RxEventCallback` 在**半传输**时也会被调用，此刻接收仍在进行，`Size` 只是"填到一半"，不是"收完了" | `UART_DMARxHalfCplt()`（`stm32f1xx_hal_uart.c:3104`）只置 `RxEventType = HAL_UART_RXEVENT_HT` 后**直接回调**，不 abort DMA、不改 `RxState`；IDLE/TC 路径才会先 abort 再回调 | `usart.c` 回调首行判 `huart->RxEventType == HAL_UART_RXEVENT_HT` → 直接 `return`，数据留到 IDLE/TC 再上交 | **实测**（2026-11-02，含反向对照，见 §9.5） |
| 2 | **seq8 清零回跳** | 上位机下发 `reset` 后，采样序号从 255 跳回 0，被误判成"丢了 255 个样本" | SAMPLE 载荷第 9 字节的 seq8 原来取 `stats.sample & 0xFF`，而 `reset` 命令会把这个计数清零 | `app_task.c` 的 `ctx_reset_stats()` 清采样计数；修前 `emit_sample()` 直接用它算 seq8 | 新增独立计数器 **`sample_seq`**（`reset` 有意不清），seq8 改取 `sample_seq & 0xFF` | 静态可证 |
| 3 | **帧头 SEQ 无人检查** | 整帧丢失**完全不可见**：CRC 只能发现"内容被改坏"，发现不了"帧根本没到" | 上位机只解析载荷里的 seq8，从不看帧头 SEQ；且帧头 SEQ 修前是各模块各发各的，ACK 还回显命令序号，根本无法用于连续性判断 | 修前 `main.py` 无 `expected_frame_seq` 字段；固件 `emit_frame()` 各自 `s_ctx.frame_seq++` | 固件：所有出站帧共用 `app_task_next_frame_seq()`；上位机：`expected_frame_seq` + `frame_gap_count`，遇到 BOOT 帧重新对齐 | 静态可证 |
| 4 | **命令 SEQ 恒为 0** | 上位机发出的每一条命令，帧头 SEQ 都是 0 | `_next_seq()` 取 `self.parser.frames`，但真实串口的数据由 `LinkWorker` 内部**另一个** `FrameParser` 解析，`MainWindow.self.parser` 只在演示模式被喂数据 | `main.py` 中 `self.parser.feed()` 仅出现在 `_feed_demo()`；`link.py:37` 在子线程里自建 `FrameParser` | 上位机改用独立计数器 `_tx_seq` | 静态可证 |

> 第 2、3 条是同一个思路的两面：**"序号"必须只表达一件事**。
> `sample_seq` 只表达"第几个样本"（reset 不能动），帧头 SEQ 只表达"第几帧出站"（全体共用）；
> 混用就会让上位机的统计失去意义。

### 7.3 四处关键设计（不是本轮修复，也未经实测）

下表是**项目成型时就定下的设计**，不是这一轮修的东西。

其中第 1 条（HT）后来已由 §9.5 实测覆盖，其余四条仍未实测。

| # | 如果不这样做（风险，推演） | 根因 | HAL 依据 | 本项目做法 |
|---|---|---|---|---|
| 1 | DMA 在跑，但采样环恒为空，上位机一帧都收不到 | HAL 只把 ADC 结果搬进 `s_dma_buf`；"取走并投递"必须由用户在回调里完成 | `ADC_DMAConvCplt()`（`stm32f1xx_hal_adc.c:2333`）只更新状态并调 `HAL_ADC_ConvCpltCallback()`；HAL 不搬运、不缓存样本 | `adc.c` 实现 `ConvHalfCpltCallback` / `ConvCpltCallback` / `ErrorCallback` |
| 2 | 连续发帧时偶发 `HAL_BUSY`，整帧丢失 | `HAL_UART_Transmit_DMA()` 上一帧未完成时不排队，直接返回 `HAL_BUSY` | 函数首行 `if (huart->gState == HAL_UART_STATE_READY)`，否则返回 `HAL_BUSY` | `app_tx.c` 单帧串行：发完（`TxCpltCallback`）才取下一批 |
| 3 | 接收不定长命令时，短帧要等缓冲填满才上交 | F1 的基础 DMA 接收没有"不定长"语义 | `HAL_UARTEx_ReceiveToIdle_DMA()` + `RxEventCallback()`：IDLE/TC 先 abort DMA、置 `RxState = READY` 再回调 | `usart.c` 用 `ReceiveToIdle_DMA`，只处理 IDLE/TC，忽略 HT（见 7.2 第 1 条） |
| 4 | 一次噪声（ORE）之后接收/采样永久停摆，且无任何提示 | HAL 的错误路径只回调，**不会自动重启**传输 | `ADC_DMAError()` 只置 `HAL_ADC_STATE_ERROR_DMA` 并回调 weak 空函数 | ADC：ISR 只置标志 → 主循环 `ADC1_RecoverInit()` + `app_measure_start()`，限速 1 s；串口：`ErrorCallback` 清 ORE，且**仅在 `gState != BUSY_TX` 时**释放发送队列 |

第 3、4 条最容易踩的坑是同一处：**错误回调里不能无条件重置发送状态**。
接收侧的 ORE/FE/NE 也会进 `HAL_UART_ErrorCallback`，此时 TX DMA 可能还在跑；
把 `s_busy` 清零会让主循环立刻再调 `HAL_UART_Transmit_DMA()` 并拿到 BUSY，
这批已出队的数据就被误记成"丢弃"——既真丢数据，又让统计失真。

### 8.2 这组数据证明了什么

- **ADC 的电压精度/线性**：只证明了"帧在流动"，没有用标准源比对读数

- **抗干扰**：没有注入噪声、没有带电拔插
- **告警滞回是否合适**：表里那个 36 是 `alarm.change_count` 的**累计值**
  （测试开始时设备已连续跑约 20 分钟），**不能读成"10 分钟内切换了 36 次"**。
  本次窗口的首末值当时没有记录，所以严格讲：**这 10 分钟内的切换次数是未知的**。
  现有旁证只有两段：10:32 读到 36、10:37 读到 40（5 分钟 +4），
  以及 10:39 起的 94 s 窗口内增量为 0。
  要判断滞回是否偏窄，应用 `soak.py` 记录首末 `changes` 求差，同时在阈值附近缓慢来回调。

### 8.4 STAT 帧数量的复核（2026-11-02 10:37 追加）

**结论：固件按 1 Hz 发 STAT，没有丢；10 分钟记录里"只有 10 条"是打点方式，不是收帧数量。**

原因在当初那个临时采集脚本：它**每收到一帧 STAT 就覆盖同一个 `stat` 变量，只在整 60 s 的刻度上打印一次**
（`if elapsed >= next_mark: ...; next_mark += 60.0`）。所以 10 分钟只有 10 行输出，
每行是**那一瞬间的 STAT 快照**，不是"10 分钟只来了 10 帧"。

为把这件事钉死，重新做了两次独立复测（串口直连，逐帧计数）：

| 复测 | 时长 | SAMPLE | STAT | STAT 频率 |
|---|---|---|---|---|
| A（`docs/SOAK_STAT_1MIN.txt`） | 61.1 s | 6106（100.00 Hz） | **61** | **1.00 Hz** |
| B（临时探针，仅打印） | 94 s | 9394（99.9 Hz） | **94** | **1.00 Hz** |

对照固件：`app_config.h:26` `APP_STAT_PERIOD_MS = 1000u`，
`app_task.c:449` 以 `tick_ms - stat_last_ms >= APP_STAT_PERIOD_MS` 为条件触发。
10 分钟理论约 600 帧，与"每 60 s 打印一次"完全不是一回事。

**顺带确认的另一点**：复测 A 中 EVENT 帧为 0，而 STAT 里 `changes` 是 40。
这不是 EVENT 丢帧 —— 那 40 是**开机以来的累计值**，复测窗口内 `changes` 增量为 0（窗口内没有状态跳变）。
代码上 `app_alarm_update()` 里 `change_count++` 与"返回新级别"发生在同一分支，
而 `process_sample()` 一旦发现 `level != last_level` 就调用 `emit_event()`，
因此**每一次切换必然对应一帧 EVENT**，不存在只在计数里加、不发帧的情况。

**工具已入库**：`host/tools/soak.py`（本次新增）按帧类型分别计数并输出频率，
不再有"每 60 s 只打一行"的歧义。用法：

```bat
python host\tools\soak.py            :: 默认 10 分钟
python host\tools\soak.py 1 COM5     :: 60 秒
```

输出末尾会直接给出 `STAT 帧 : N (x.xx Hz，设计 1.00 Hz)`，低于 1 Hz 就说明 STAT 真的在丢。

#### 9.1.1 为什么"请求 3 秒"实际跑了 4.69 秒

不是采集变慢，是**读循环的粒度问题**：

```python
chunk = ser.read(8192)      # 旧写法
```

本机（Windows + CH340 + pyserial 3.5）实测：`read(n)` 会**一直累积到凑满 n 字节才返回**，
数据持续流入时不在 timeout 处停下。链路上约 1.7 KB/s（100 Hz × 17 B），凑满 8192 B 需要
**4.7 s**，于是循环总是晚一个读周期才退出（机制未查证，只记录现象）：

| 请求时长 | 实际时长 | 多出 |
|---|---|---|
| 3 s | 4.69 s | 一个读周期 |
| 5 s | 9.41 s | 两个读周期 |

已改为按 `ser.in_waiting` 取，修复后实测 `真实时长 3.00 s / 300 样本`。
**数据本身不受影响**：均值是对 468 帧求的，只是"时长"这个标签当时写错了。

### 9.4 误差分析（这两点能说明什么、不能说明什么）

| 指标 | 数值 | 说明 |
|---|---|---|
| 零点偏移 | **+1.75 mV（+2.2 LSB）** | ADC 内部偏移 + 地线压降，量级正常 |
| 满量程读数 | 3299.87 mV（4094.8 LSB，复测） | 与理想 3300 差 −0.13 mV（−0.004%） |
| 跨度（span） | 3299.87 − 1.75 = **3298.12 mV** | 相对 3300 偏小 1.88 mV（**−0.057%**） |
| 零点噪声 | 峰峰 **9 mV（11 LSB）** | 约 ±5 mV，占 WARN 阈值 0.2% |

**能说明**：零点偏移约 2 LSB、跨度误差 0.06%，对 2400 / 3000 mV 的阈值判断完全够用；
ADC 与 `raw*3300/4095` 的换算在两端都没有明显偏差。

**不能说明**：

- **不是"全量程线性度 0.06%"** —— 只测了两点，只能算一个端点直线，中间段（25%/50%/75%）
  没测，非线性误差未知。
- **满量程的"峰峰只有 1 mV"不代表噪声更小**：输入顶在 VREF 上时，ADC 输出在 4094/4095
  之间钳位，峰峰被饱和截断。零点那 9 mV 才是真实的噪声水平。两处数字不可比。
- **这是"比例测量"，不是绝对电压校准**：STM32F103C8T6（LQFP48）内部 **VREF+ 与 VDDA
  是同一条电源**，PA1 接板载 3.3V 时，ADC 的参考和输入是同一个节点。所以 4095 满码
  只能证明"ADC 满码与 `raw*3300/4095` 换算正常"，**不能证明板上 3.3V 真的等于 3.300V**。
  要标定绝对精度得用万用表实测 VDDA 再比对（已列入 §4.2）。

| `uart_err` / `frm` | 0 / 0 | 0 / 0 | 无 |

#### 9.5.3 关键结论：数 ERR 行抓不到这个 bug

最初那版测试只数 `ERR unknown command` 的行数，**它对这个 bug 没有判别力**，原因是：

> HT 上交的是**前 32 字节**，其中不含 `\r\n`。重复交付的两段 32+48 字节会**拼进同一行**，
> 所以最终仍然只产生**一行** ERR —— 重复只能从"这一行变长了"看出来，从行数上看不出来。

真正有判别力的是另外两项：

| 判别指标 | 原理 | 修复版 | 旧行为 |
|---|---|---|---|
| `rxf` 增量 | HT 时 `rearm` 撞 `RxState == BUSY_RX` → `HAL_BUSY` → `s_rx_fail++` | 0 | +10（每条命令 +1） |
| 回显长度 | 同一批字节被上交两次，行内容被拼接 | 69（21 + 48） | 84（拼接后被 63 字符上限截断） |

所以 `htcheck.py` 已加上回显长度的断言，两个指标同时成立才算 PASS——
**只断言一个"看起来是 0"的数字，等于没测**（和当初给 `gui_smoke` 加注入缺口是同一个教训）。

#### 9.5.4 这条证据能说到什么程度

- ✅ 修复版行为正确（两项独立指标）；
- ✅ 测试有判别力（去掉修复后两项同时报警）；
- ⚠️ 只覆盖 48 字节这一种长度；更长命令会被 64 字节行缓冲截断，属设计行为，未在此测；
- ⚠️ 反向对照是在**本机临时改代码**做的，那个 `# TEMP-EXP` 版本没有提交，
  仓库里只有修复版（`Code=20700`）。实验记录见 `docs/CALIB_20261102.txt` 第 4 节。

工具：`host/tools/htcheck.py`（A/B 对照 + `rxf` + 回显长度三项断言，可复跑）。

## 10. 上位机串口读取修复（2026-11-02）

做真机界面截图时发现：连上 COM5 跑 6 s 只统计到 **468 点**（应约 600），界面每两三秒才跳一次。

根因与 `calib.py` / `soak.py` 是同一类：`SerialWorker.run()` 里用的是

```python
data = self._ser.read(4096)
```

本机（Windows + CH340 + pyserial 3.5）实测观察到：`read(n)` 会**累积到凑满 n 字节才返回**，
数据持续流入时不在 timeout 处停下。链路约 1.7 KB/s，凑满 4096 B 要 **2.3 s** ——
所以界面表现为"卡 2 秒、然后涌一批"。**具体机制与驱动/版本的关系尚未查证**，这里只记录现象；
改用 `in_waiting` 后现象消失。

| | 修复前 | 修复后 |
|---|---|---|
| 6 s 统计点数 | 468（≈78 Hz） | — |
| 16 s 统计点数 | — | **1597（≈99.8 Hz）** |
| 首帧延迟 | ≈2.3 s | < 10 ms |

修法：`n = in_waiting; 为 0 就 sleep 5 ms; 否则 read(n)`。

> 这个缺陷只在"真串口 + 界面"这条路径上暴露，`--demo` 与协议单测都碰不到——
> 这也是之前 §5 里"GUI 未接真实串口"那行必须诚实标注的原因。

同一轮还修了坐标轴的显示问题：pyqtgraph 默认给刻度加 SI 前缀，于是时间轴被写成
`1.6 ks`、电压轴 `3 kmV`。对固定单位（秒 / 毫伏）来说这层换算毫无意义，还会让读数字
的人多绕一道。已对两条轴调用 `enableAutoSIPrefix(False)`，现在直接显示 `1600 s` / `3000 mV`。
两张截图（`gui_demo.png`、`gui_real_serial.png`）均已按修复后的界面重新生成。

## 11. 演示源与冒烟截图的两处修正（2026-11-02）

用户逐像素看 `gui_demo.png` 时发现两处破绽，都成立。

### 11.1 截图在事件循环之外抓 → 顶部变成"未连接"

`gui_smoke.py` 的 `win.grab()` 原来写在 `app.exec()` 之后。退出后窗口会走
`closeEvent -> _disconnect()`，于是：

- 顶部标签从琥珀色的「演示模式（无硬件）」变成红色的「未连接」；
- 右侧「运行时间」停在最后一条 STAT（3.0 s），而「采样数」已经跑到 4 秒的量。

修法：截图与所有取值都放进 `QTimer` 回调，在 `app.quit()` **之前**完成。
另加一条断言：顶部状态必须包含「演示模式」，否则 FAIL——这样同类问题下次会自己暴露。

### 11.2 演示源判级没有滞回 → 事件表自相矛盾

`DemoSource._tick()` 原来是无回差的简单比较：

```python
lvl = 0
if filt >= self.crit: lvl = 2
elif filt >= self.warn: lvl = 1
```

于是事件表里出现 `WARN -> NORMAL | 2394 mV`，而固件的退出条件是要掉到
`warn - 50 = 2350` 以下。同一份材料里两个判级规则不一致，是最容易被抓的那种破绽。

改为与固件一致的**相邻级别跳转 + 50 mV 回差**（`THR_HYST_MV`）：

```python
lvl = self.level
if lvl == 0:
    if filt >= self.warn:            lvl = 1
elif lvl == 1:
    if filt >= self.crit:            lvl = 2
    elif filt < self.warn - THR_HYST_MV: lvl = 0
else:
    if filt < self.crit - THR_HYST_MV:   lvl = 1
```

### 11.3 时间轴对齐

`DURATION_MS` 由 4000 改为 **4050**：STAT 是 1 Hz，多等 50 ms 让 `t = 4000 ms` 那条
STAT 被处理，避免截图里"运行时间 3.0 s / 采样 400 点"看着像丢了数据。

### 11.4 重跑结果

```
顶部状态      : 演示模式（无硬件）
采样点        : 400
告警事件行数  : 2
事件 1        : 770 ms  NORMAL -> WARN    2412 mV   （≥ 2400，进入 WARN）
事件 2        : 2040 ms WARN -> NORMAL    2348 mV   （≤ 2349，退出 WARN）
RESULT: PASS
```

两条事件的数值都落在 50 mV 回差允许的区间内，与固件规则一致。

### 21.2 判定

> 百分比一律以 **FS = 3300 mV**（固件满量程）为分母；以表读数为分母的比值另标"相对读数"，不叫 %FS。

| 跨度误差 | +53.17 mV ＝ **1.61 %FS** | ≤0.5 %FS（16.5 mV） | **FAIL（点估计）** |

### 21.3 误差归因：只能说"一致"，不能说"验证"

**PA1 接轨时，输入就是 VDDA 本身**，ADC 必然满码（本轮均值 4094.7 LSB，即 4094–4095），
固件按 `4095 × 3300 / 4095 = 3300 mV` 折算，于是：

```
54.75 mV = 3300 − 3245
```

这是一个**算术恒等式**，不是对 ADC 增益的独立验证。它成立的唯一含义是：
"设备读数比外部表读数高 54.75 mV"，且这个差**与"固件假设 3.300 V、而轨压更低"一致**。

**在表不确定度（±28.0 mV）内，无法区分两种解释**：

| 解释 | 也能解释这 54.75 mV 吗 |
|---|---|
| **板偏**：VDDA 真的只有 3.245 V，ADC 增益准确 | 能 |
| **表偏**：VDDA 其实是 3.30 V 附近，表读数偏低 55 mV | 能 |

因此**本轮不给出"ADC 自身增益误差 < 0.3 LSB"这类结论**（早期草稿写过，已撤回）。
要分离两者，必须做**比例测量**：同一量程下读 PA1 实际电压与 VDDA，验证 `mv_fw ≈ V_PA1/VDDA × 3300`（见 §21.5）。

**不确定度边界**：表标称 ±(0.8 % 读数 + 2 字) ⇒ 3.245 V 处约 **±28.0 mV（±0.85 %FS）**，
满量程误差真实区间 **+26.79 ~ +82.71 mV ＝ +0.81 % ~ +2.51 %FS**，跨过 1 % 门槛。
故只能写"**点估计超标、机制一致但未分离**"，**不能写"确定超过 1 %FS"，也不能写"已验证 ≤1 %FS"**。
另注：**±28.0 mV 本身也是估计**——表型号与量程未记录，精度公式来自用户口述，未核对说明书原件。

### 21.4 一个此前未记录的连带影响

设备读数 `mv_rep = V_in × 3300 / 3245 = V_in × 1.016949`，所以**告警阈值在真实电压上系统性偏低 1.69%**：

| 标称阈值 | 真实触发点 |
|---|---|
| `WARN 2400 mV` | **2360.0 mV** |
| `CRIT 3000 mV` | **2950.0 mV** |

对"是否报警"没有影响（读数与阈值同口径），但任何"绝对电压"表述都要带这个偏差。
