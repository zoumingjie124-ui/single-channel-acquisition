## 1. 当前数据流与模块调用关系

### 1.1 链路

```
TIM3(TRGO, 100Hz) ──► ADC1 ──► DMA1_CH1(循环, 半字, buf=2)
                                      │
                        ┌─────────────┴─────────────┐
                        │ ISR（只搬指针，μs 级）      │
                        │  app_measure_on_half()    │  → s_ring[64]
                        │  app_measure_on_cplt()    │
                        │  app_measure_on_error()   │  → 只置 s_recover_req
                        └─────────────┬─────────────┘
                                      │
主循环 while(1) → app_task_run()
   ├─ 1  app_cmd_poll(tick_ms)            命令解析（含 50ms 半帧超时复位）
   ├─ 2  for(n<8) app_measure_pop(&raw)   从环里取样本
   │        └─ process_sample(raw)
   │             ① mv_raw  = app_measure_raw_to_mv(raw)     ← 原始值（mV）
   │             ② mv_filt = app_filter_push(&filter, mv_raw) ← 滤波值（mV）
   │             ③ level   = app_alarm_update(&alarm, mv_filt) ← 只看 filt
   │             ④ 级别变化 → emit_event()
   │             ⑤ emit_sample(mv_raw, mv_filt, level, seq8)
   ├─ 3  按键 → emit_stat()
   ├─ 4  周期 1s → emit_stat()
   ├─ 5  app_measure_poll_recovery()      ADC 故障恢复（限速 1s）
   ├─ 5.5 usart_rx_guard(tick_ms)         RX 重挂守护（限速 200ms）
   ├─ 6  app_tx_poll()                    推动 DMA 发送
   └─ 7  update_led()
```

### 1.2 关键事实（都有代码/实测出处）

| 项 | 值 | 出处 |
|---|---|---|
| 采样周期 / 频率 | **10 ms / 100 Hz** | `app_config.h:24 APP_SAMPLE_RATE_HZ=100`；实测 100.010 Hz（§17） |
| 原始值 `mv_raw` | `app_task.c` `process_sample()` 第一步 | `app_measure_raw_to_mv()`（`app_measure.c:237`，`raw*3300/4095`） |

### 1.3 时间预算（为什么加诊断不会破坏时序）

一次 `process_sample()` 现在做：1 次乘除（`raw*3300/4095`）+ 8 点滤波（2 次加减）+ 状态机比较 + 1 帧 16 B 组帧（CRC16 逐字节，16 次循环）+ 一次 memcpy 入发送环。
100 Hz 下总共约 **几百微秒/秒** 量级，相对 10 ms 周期余量极大（1 小时长跑每分钟精确 6001 帧、0 丢点，§17）。

新增诊断若做到 **O(1)/样本**（见 §4 的增量实现），每样本增量约十几条指令，
占比可忽略。**但必须实测确认**：加完后重跑 10 分钟长跑，看是否仍是 100.0x Hz / drops 0。

## 2. 三类故障的检测算法建议

### 2.1 传感器输入异常

#### 2.1.1 先说清楚哪些能测、哪些不能

| 子类 | 当前硬件能否检测 | 说明 |
|---|---|---|
| 短接 GND | ✅ 能 | 读数被拉到 ~0 mV（实测零点 +1.75 mV） |
| 短接 3.3V 轨 | ⚠ 能测到，但**语义上不可区分** | 读数 3299.87 mV，与"合法满量程输入"电气上完全一样。只能报"持续贴上限"，是否算故障取决于应用 |
| 接近上下限 | ✅ 能 | 同上，作为"观察项"上报更合适 |
| ADC 超量程 | ❌ 物理上看不到 | F1 的 ADC 在 >VREF+ 时输出钳位在 4095，**过驱信息丢失**，只能看到"贴上限" |
| **输入断线（悬空）** | ❌ **不能可靠检测** | PA1 配置为 `GPIO_MODE_ANALOG` + 无上下拉（`gpio.c` / `CUBEMX_CONFIG.md`），悬空时读数不确定（可能飘在中值、也可能贴边、还可能是噪声）。**没有可预期的"特征值"就无法判据** |

> 断线要可靠检测，标准做法是给输入加**偏置电阻**（例如 100 kΩ 下拉，断线时稳定读 ~0 mV；或上拉到 VREF/2，断线读 ~1650 mV），
> 用"稳定停在偏置值"作为判据。**这需要改硬件，不在本轮范围，需你决策。**

#### 2.1.2 算法（短接到轨 / 接近极限）

```
每样本（用 raw_mv，不用 filt_mv——滤子有 40ms 延迟，且会把"贴边"抹圆）：
    if mv_raw <= INPUT_LOW_MV   → low_cnt++  else low_cnt  = 0
    if mv_raw >= INPUT_HIGH_MV  → high_cnt++ else high_cnt = 0
    if low_cnt  >= INPUT_CONFIRM_SAMPLES  → 置 INPUT_LOW  故障
    if high_cnt >= INPUT_CONFIRM_SAMPLES  → 置 INPUT_HIGH 故障
    if low_cnt == 0 && high_cnt == 0      → recover_cnt++
    if recover_cnt >= INPUT_RECOVER_SAMPLES → 清故障
```

阈值依据（**必须写清楚，不许拍脑袋**）：

| 参数 | 建议值 | 依据 |
|---|---|---|
| `INPUT_LOW_MV` | **50 mV** | 实测静置峰峰 11 mV（σ 2.40）的 4.5 倍 + 零点偏移 1.75 mV；远离 WARN 阈值 2400 mV。**待确定**：若传感器正常输出包含 0–50 mV，此值必须上调 |
| `INPUT_HIGH_MV` | **3270 mV** | 实测接 3.3V 轨读数 3299.87 mV，留 30 mV 余量（≈3× 满量程噪声 1 mV 峰峰）。**待确定**：若传感器可能合法达到满量程，此阈值失去判别力 |
| `INPUT_CONFIRM_SAMPLES` | **100（=1 s）** | 8× 滤波窗口（80 ms）+ 远大于告警去抖 3 点（30 ms）；1 s 也正好是 STAT 周期，便于与上报对齐 |
| `INPUT_RECOVER_SAMPLES` | **50（=0.5 s）** | 故障恢复要快于触发（避免"故障已消失还在报"），但仍需足够样本防止在阈值边界抖动导致状态翻转 |

**抖动保护**：在 `INPUT_LOW_MV` 与 `INPUT_HIGH_MV` 内侧各留 20 mV 的回差带，
进入需越外限、退出需回到内限——与 `app_alarm` 的滞回思路一致（`APP_THR_HYST_MV` 已是 50 mV，这里取 20 mV 是因为输入类不需要那么宽的滞回）。

**ADC 贴边码值**（观察项，不单独判故障）：`raw <= 2` 或 `raw >= 4093`，
依据是实测零点均值 2.2 LSB、满量程均值 4094.8 LSB。它只说明"贴着量化边界"，不能说明是故障，故设计为**只上报、不告警**。

### 2.2 信号卡死

#### 2.2.1 为什么不能用"逐样本比较"

若用"连续 N 个样本两两差值都 < DELTA"，实现要维护一个 N 深窗口，且**滑窗 min/max 不是 O(1)**。
本工程主循环余量虽大，但没理由为诊断引入 O(N) 扫描。

#### 2.2.2 推荐实现：分块 + 块内极值（O(1)/样本）

```
维护一个 1 秒的块（BLOCK = 100 样本）：
    每样本：blk_min = min(blk_min, mv_raw); blk_max = max(blk_max, mv_raw)
    块结束时：
        span = blk_max - blk_min
        if span < STUCK_DELTA_MV  → stuck_blk++  else stuck_blk = 0
        if stuck_blk >= STUCK_CONFIRM_BLOCKS → 置 SIGNAL_STUCK 故障
        blk_min = 0xFFFF; blk_max = 0        （重置，否则极值累积永远触发不了）
```

- 每样本 2 次比较，**O(1)**；
- 检测延迟 = `BLOCK × STUCK_CONFIRM_BLOCKS`；
- **块内极值必须重置**，这是最容易写错的地方（不重置会导致 `span` 单调增长、永远大于阈值，故障再也不触发）；
- 用户要求的"连续 N 秒变化幅度低于设定值" = `BLOCK(1s) × STUCK_CONFIRM_BLOCKS`，
  取 `STUCK_CONFIRM_BLOCKS = 3` → **N = 3 s**（3–4 s 内检出）。

#### 2.2.3 阈值依据

| 参数 | 建议值 | 依据 |
|---|---|---|
| `STUCK_DELTA_MV` | **50 mV** | 必须 > 实测静置峰峰 11 mV 和电位器接触噪声峰峰 18 mV；50 mV 也 ≈ 1/66 满量程。**待确定**：一个真正稳定的传感器（恒压供水、恒温箱）在 3 s 内变化 < 50 mV 是**完全正常的**，此时会误判 |
| `STUCK_BLOCK_MS` | 1000 | 与 STAT 周期对齐，便于人工比对 |
| `STUCK_CONFIRM_BLOCKS` | 3 | 见上，N = 3 s |
| 恢复条件 | **连续 2 个块 span ≥ DELTA** | 单块恢复太敏感：一次噪声尖峰就能把真故障清掉（实测接触噪声可达 +38 mV 单步）。要求 2 块 = 2 s，代价是恢复延迟 2 s |

#### 2.2.4 正常稳定输入被误判——三个缓解手段

1. **默认关闭**：`STUCK` 检测需要一个使能位，主机不下发就不跑。这是最有效的缓解。
2. **报"疑似"而非"确认"**：把 `span` 实测值一起上报，让上位机/人判断"这个信号本来就不会动"。
3. **与 `SAMPLE_STARVED` 分开**：卡死 = "有值但不变"；停摆 = "没值"。
   两者成因与处置完全不同（后者由 Stage 1 的 ADC 恢复 + RX 守护覆盖），
   混为一个故障码会让排查变乱。

### 2.3 变化率异常

#### 2.3.1 算法

```
每样本（用 raw_mv，理由见下）：
    d = |mv_raw - mv_raw_prev|
    mv_raw_prev = mv_raw
    if d > ROC_LIMIT_MV  → roc_cnt++  else roc_cnt = 0
    if roc_cnt >= ROC_CONFIRM_SAMPLES → 置 RATE_HIGH 故障
    if roc_cnt == 0 持续 ROC_CLEAR_SAMPLES 个样本 → 清故障
```

- `ROC_CONFIRM_SAMPLES = 3`（30 ms）：**连续 3 个样本**都超限才算。
  单样本毛刺（实测接触噪声最大 +38 mV 单步）过不了这一关；
- `ROC_CLEAR_SAMPLES = 20`（200 ms）：恢复也要连续确认，避免在阈值边界来回翻。

#### 2.3.2 为什么用 raw 而不是 filt

- 用 `filt_mv`：8 点均值会把一个真实阶跃**摊薄成 8 步**（第一拍只出 1/8 幅度），
  且群延迟实测 40 ms。也就是说滤波后测变化率，**既晚又小**，阈值很难定；
- 用 `raw_mv`：直接反映跳变，代价是要和噪声共处——所以阈值必须远大于噪声（见下）。
- **注意与限幅滤波的互斥**：`APP_RATE_LIMIT_MV` 当前是 `0`（关闭）。
  一旦开启限幅，真实快变会被削平，**变化率故障就永远测不到**。
  若将来两者都要用，必须保证 `APP_RATE_LIMIT_MV > ROC_LIMIT_MV`。

#### 2.3.3 阈值依据与误报分析

| 参数 | 建议值 | 依据 |
|---|---|---|
| `ROC_LIMIT_MV` | **200 mV** | 5× 实测最大接触噪声单步（38 mV）；≈ 满量程 1/16；≈ 83 LSB，远离量化与噪声（σ 2.40 mV）。**待确定**：真实传感器的最大上升沿决定了这个值，电位器拧一下能产生 >1000 mV/样本，属"合法快变" |
| `ROC_CONFIRM_SAMPLES` | 3 | 见上 |
| `ROC_CLEAR_SAMPLES` | 20 | 见上 |

**必须讲清楚的两类误报**：

1. **正常突变**：电位器从 0 猛拧到 3.3 V，单样本变化可达上千 mV，任何变化率检测都会触发。
   这不是误报也不是漏报——**变化率故障只有在"过程有已知最大斜率"时才有意义**。
   若没有这个先验，应把它定义为**事件**（记录 + 上报，不判故障）。
2. **噪声 + 滤波延迟**：见 §2.3.2，用 raw 就绕开了滤波延迟问题；
   噪声问题靠"阈值远大于噪声 + 连续 3 样本确认"解决。

## 3. 六个问题的直接回答

### 3.1 ADC 原始值和滤波值分别在哪里获取？

- `raw`：ADC 原始码（u16，0–4095）由 DMA 写入 `s_dma_buf`，ISR 搬进 `s_ring`，
  主循环 `app_measure_pop(&raw)` 取出；
- `mv_raw`：`app_measure_raw_to_mv(raw)`（`app_measure.c:237`）= `raw*3300/4095`；
- `mv_filt`：`app_filter_push(&s_ctx.filter, mv_raw)`（`app_task.c` `process_sample()` 第二步）。

**诊断要同时拿到这两个值**，且必须在 `app_filter_push()` **之后**、
`app_alarm_update()` **之前或之后都行**（本方案取"之后"，这样告警级别已算完，诊断可以顺带在帧里带上当前级别，便于上位机对照）。

### 3.2 当前采样频率和采样周期？

**100 Hz / 10 ms**（TIM3 TRGO）。实测 100.010 Hz（§17，1 小时总账），
3503 个相邻 `t_ms` 间隔全部等于 10 ms（Stage 2）。
所有"确认时间"都按"样本数 = ms/10"换算，避免引入新的时基。

### 3.3 故障诊断适合放在哪个模块？

**新增 `App/Src/app_diag.c` + `App/Inc/app_diag.h`**，理由：

| 候选 | 评价 |
|---|---|
| 塞进 `app_alarm.c` | ❌ 告警是"电平判级"，故障是"行为判异"，语义不同；且会动已验证模块 |
| 塞进 `app_filter.c` | ❌ 滤波是纯函数式变换，无状态机；且 Stage 4 的 167 断言都建立在它现有行为上 |
| 塞进 `app_measure.c` | ❌ 那是 ADC 隔离层，混入诊断会让"恢复"和"判异"缠在一起 |
| **新增 `app_diag.c`** | ✅ 纯逻辑、无 HAL 依赖 → **能进 `fw_tests/` 用 GCC 单测**（和 Stage 4 同一套办法）；不依赖 HAL 意味着不碰任何已验证路径 |

`app_diag.c` 的输入只有 `(mv_raw, mv_filt, tick_ms)`，输出是"故障位图 + 每故障的实测值"，
**不回写、不改任何现有模块的状态**。

### 3.4 是否会影响现有滤波、阈值报警和 DMA 采样时序？

| 对象 | 影响 | 说明 |
|---|---|---|
| DMA 采样时序 | **无** | 硬件触发 + 循环 DMA，与主循环在做什么无关；主循环只从环里取 |
| `app_filter.c` | **无** | 不改代码、不改参数，诊断只读它的输出 |
| `app_alarm.c` | **无** | 不改代码；且**不让告警级别参与故障判定**（避免语义耦合） |
| 主循环耗时 | 有增量，需实测 | O(1)/样本，预估十几条指令/样本；**加完后必须重跑 10 分钟长跑**确认仍是 100.0x Hz、drops 0 |
| 上报带宽 | 有增量 | 见 §6.2：默认关闭时不发任何新帧；开启后按 1 Hz 发 FAULT 状态帧（8 B/s），对 13.9% 的带宽占用可忽略 |

### 3.5 当前 UART 协议如何增加故障码和故障状态？

已核对现有协议（`app_proto.h:29-47`）与上位机解码（`host/protocol.py:310-330`），结论：

1. **不要改 `STAT`（37 B）和 `SAMPLE`（10 B）的长度** —— 协议文档明确"严格按长度校验，
   长度不匹配就丢帧"，改长度会让旧上位机直接丢帧。
2. **新增帧类型 `PROTO_T_FAULT = 0x86`**，分两种：
   - **FAULT 事件帧**（状态跳变时发，类似 EVENT）：`code(1) state(1) value_mv(2) t_ms(4)` = **8 B**，与 EVENT 等长，上位机事件表可直接复用；
   - **FAULT 状态帧**（跟随 STAT，1 Hz）：`fault_map(2) raw_min(2) raw_max(2) last_d(2)` = **8 B**，让上位机随时能看到当前位图与诊断实测量。
3. **新增命令 `PROTO_T_SET_DIAG = 0x15`**：`enable_map(2) + 各故障参数`。
   **默认 `enable_map = 0`**——主机不下发就完全不诊断、不发新帧，
   现有行为逐字节不变（Stage 1–6 的回归基线继续有效）。
4. **兼容性**：旧版 `protocol.py` 的 `decode_many()` 对未知类型是**静默跳过**
   （`protocol.py:311-330`，没有 `else: errors += 1`），所以即使旧主机连上新固件，
   也**不会**冒出一堆"解析错误"，只是看不到故障信息。这一点降低了升级风险。

### 3.6 上位机是否需要同步修改？

**需要，且必须与固件同一次提交**（否则 `test_firmware_sync.py` 的常量一致性检查会挂）：

| 文件 | 改动 |
|---|---|
| `host/protocol.py` | 新增 `T_FAULT = 0x86`、`T_SET_DIAG = 0x15`、`parse_fault_event()` / `parse_fault_stat()` |
| `host/main.py` | 新增"故障诊断"面板：当前故障位图、每故障实测值、事件表新列；开启/关闭诊断的开关 |
| `host/tests/test_protocol.py` | 新增 FAULT 帧编解码用例 |
| `host/tests/test_firmware_sync.py` | 把新的常量/长度加入一致性检查（**这一步不能漏**） |
| `host/tools/diag_inject.py`（新） | 故障注入工具（软件注入，见 §7.1） |
| `fw_tests/test_diag.c`（新） | `app_diag.c` 的 C 单元测试（GCC，复用 Stage 4 框架） |

## 4. 故障码设计建议

### 4.1 编码规则

按"类别 + 序号"分段，留足扩展位；位图用 `uint16`（当前用 6 位，剩 10 位预留）。

| 码 | 名称 | 类别 | 默认启用 |
|---|---|---|---|
| `0x11` | `INPUT_LOW` | 输入异常 | 是 |
| `0x12` | `INPUT_HIGH` | 输入异常 | 是 |
| `0x13` | `INPUT_SAT` | 输入异常（**观察项，不判故障**） | 是 |
| `0x21` | `SIGNAL_STUCK` | 信号卡死 | **否（易误报）** |
| `0x31` | `RATE_HIGH` | 变化率异常 | 否 |
| `0x41` | `SAMPLE_STARVED` | 采集停摆（无样本） | 是 |
| `0x51` | `ADC_RECOVER_FAIL` | ADC 恢复失败（复用 Stage 1 已有计数） | 是 |

### 4.2 每故障状态机

```
状态: 0=正常  1=待确认  2=已确认  3=恢复中
正常 --(条件持续 T_confirm)--> 已确认
正常 --(条件刚满足但未满 T_confirm)--> 待确认
已确认 --(恢复条件持续 T_recover)--> 正常
```

- `待确认` 状态**不上报为故障**，只影响内部计数——避免把一次毛刺广播出去；
- 状态跳变才发 FAULT 事件帧，1 Hz 的 FAULT 状态帧负责"当前快照"，两者互补。

### 4.3 文本通道同步加一行（沿用 `ERRSRC` 的既有做法）

```
DIAG map=0x0000 stuck_span=... last_d=... raw_min=... raw_max=...
```

**单独一行**，不要并进现有 `STAT` 文本行——那行最坏情况已约 168 字符，
`tx_text()` 缓冲是 192 B（`app_task.c:63`），再并一行会把尾部截掉。

## 5. 触发 / 确认 / 恢复条件总表

| 故障 | 触发条件 | 确认时间 | 恢复条件 | 阈值依据 |
|---|---|---|---|---|
| `INPUT_LOW` | `raw_mv ≤ 50 mV` 连续 | **1 s**（100 样本） | 回到 `> 70 mV` 持续 0.5 s | 4.5× 静置峰峰 11 mV + 零点偏移 |
| `INPUT_HIGH` | `raw_mv ≥ 3270 mV` 连续 | **1 s** | 回到 `< 3250 mV` 持续 0.5 s | 实测满量程 3299.87 mV − 30 mV |
| `INPUT_SAT` | `raw ≤ 2` 或 `raw ≥ 4093` | 即时（观察项） | 离开贴边 | 实测 2.2 / 4094.8 LSB |
| `SIGNAL_STUCK` | 连续 3 个 1 s 块内 `(max−min) < 50 mV` | **3 s** | 连续 2 个块 `span ≥ 50 mV` | > 接触噪声峰峰 18 mV；**待确定** |
| `RATE_HIGH` | 连续 3 样本 `|Δraw| > 200 mV` | **30 ms** | 连续 20 样本 `≤ 200 mV` | 5× 最大接触噪声单步 38 mV；**待确定** |
| `SAMPLE_STARVED` | `tick_ms − 最近一次 process_sample 的 tick` > 500 ms | **0.5 s** | 收到新样本即清 | 50 个采样周期 |
| `ADC_RECOVER_FAIL` | `app_measure_recover_fail()` 增量 > 0 | 即时 | 恢复成功一次 | 复用 Stage 1 现有计数 |

> 表中所有"待确定"项的意思是：**在没有真实传感器参数之前，不许把建议值当成最终值**。
> 它们要么来自"先用电位器跑一遍再定"，要么来自用户提供的传感器规格书。

## 6. 故障注入测试方案

分三档，**强度递减，必须分开标注**（沿用 Stage 6 §TEST_INVENTORY 的 A/B/C 分级思路）。

### 6.1 软件注入（C 档，只证明代码路径）

在 `APP_DEBUG_INJECT` 下新增文本命令（与 `adcinject`/`rxstop` 同模式，默认不编入）：

| 命令 | 作用 | 能验证什么 |
|---|---|---|
| `diagin low` | 让诊断模块把 `mv_raw` 强制替换成 10 | `INPUT_LOW` 的触发/确认/恢复时序、帧格式 |
| `diagin high` | 强制替换成 3290 | `INPUT_HIGH` |
| `diagin stuck` | 强制输入恒定值 | `SIGNAL_STUCK` 的 3 块确认与极值重置逻辑 |
| `diagin rate` | 每样本强制跳变 500 mV | `RATE_HIGH` 的 3 样本确认 |
| `diagin starve` | 让主循环跳过 `app_measure_pop` | `SAMPLE_STARVED` |

**必须写明**：注入的是"喂给诊断模块的数值"，**不是真实电气故障**。
它能证明状态机与协议正确，不能证明"真断线时读数长什么样"。

### 6.2 跳线可做（B 档，真实电气，只需杜邦线）

| 故障 | 操作 | 注意 |
|---|---|---|
| `INPUT_LOW` | 断电后 PA1 直接接 GND，上电保持 | 断电改线；这就是 §9.2 做过的那件事 |
| `INPUT_HIGH` | 断电后 PA1 接板载 3.3V 轨，上电保持 | 与"合法满量程"不可区分，只验证检测逻辑 |
| `INPUT_SAT` | 同上，读 `raw` 是否贴 4095 | — |
| `SIGNAL_STUCK` | 电位器拧到一个值后**完全不动 10 s** | 注意：电位器本身有接触噪声，实测 span 会大于 0，这正好用来校准 `STUCK_DELTA_MV` |
| `RATE_HIGH` | 快速猛拧电位器 | 会产生合法快变 → 必然触发，用来验证"事件"语义而非"故障"语义 |
| 悬空观察 | **PA1 什么都不接**，上电读 30 s | **这是一次有价值的实验**：先用它确定"断线时读数到底长什么样"，再决定断线检测方案。当前无法预判结果 |

### 6.3 需要额外硬件（无法在本轮做）

| 需求 | 用途 | 缺它会怎样 |
|---|---|---|
| 万用表 | Stage 6 第 2 项的绝对精度（VDDA / 输入电压） | 输入类阈值的绝对依据不足 |
| 真实传感器（4–20 mA / PT100 / NTC） | 标定 `STUCK_DELTA_MV`、`ROC_LIMIT_MV` | 这两个阈值只能标"待确定" |
| 可编程信号源 / 函数发生器 | 精确验证变化率阈值与确认时间（线性斜坡 + 阶跃） | 只能用"猛拧电位器"近似，无法定量 |
| **偏置电阻（100 kΩ 级）** | 可靠检测输入断线 | 断线检测只能停留在"观察悬空读数"阶段 |
| 第二块板 / 第二个 USB-TTL | GUI 长跑与 soak 同时进行 | 两者抢同一个串口，只能二选一 |
