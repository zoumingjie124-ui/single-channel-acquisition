> 一句话结论：**加一条 `0x16 GET_DIAG` 解决"状态对不齐"，改造发送层解决"事件丢了不重发"。
> 两件事不能混——快照保证的是"当前状态"，不是"历史事件可靠投递"。**

## 0. 先给结论，再给细节

| 问题 | 本设计的答案 |
|---|---|
| 事件丢了怎么办 | 把"设备状态"与"已上报状态"分开记：`active` vs `reported`。两者不等就重发，**发成功才拉平** |
| 会不会每 10 ms 刷一帧 | 不会。三个闸门：`active==reported` 不发、队列没空间不发、100 ms 节流 |
| 断线重连怎么对齐 | `GET_DIAG` 要一帧**快照**（`event=0`），`active` 是权威值 |
| 快照会不会伪造成事件 | 不会。`event=0` 是独立取值，快照**只读**状态，不写 `reported`、不动 `app_diag` |
| 快速 确认→恢复→确认 | 状态差驱动，永远不会发出与当前状态矛盾的帧；**中间边沿可能被合并**（见 §4，需要你确认能否接受） |

## 1. GET_DIAG 协议定义

### 1.1 请求（上位机 → 设备）

| 项 | 值 |
|---|---|
| TYPE | `0x16` |
| LEN | **0**（无载荷） |
| SEQ | 命令序号，与现有命令同一套（独立于设备全局帧序号） |
| 非法情况 | `LEN ≠ 0` → ACK `result=1`，**不进回调**（与 SET_DIAG 同一套写法） |

### 1.2 应答

**两帧，顺序固定：先 ACK，后快照。**

| 帧 | 内容 |
|---|---|
| ACK `0x84` | `req_type=0x16`，`result=0`（或 1=参数错误） |
| FAULT `0x86` | `event=0` 快照，见下 |

> 顺序为什么是 ACK 在前：`app_cmd` 现有的流程是"先执行回调、再统一 `send_ack`"。
> 若在回调里直接发快照，快照会排在 ACK 前面。所以本节设计成：
> **回调只置一个"待发快照"标志**，由主循环在 `app_cmd_poll()` 之后（第 1.5 步）真正发帧。
> 这样既保证 ACK 在前，也保证快照是在**入队那一刻**才取状态的（见 §5）。

### 1.3 快照帧（复用 `0x86`，不改帧结构）

| 偏移 | 字段 | 快照时的取值 |
|---|---|---|
| 0 | `t_ms` | 发帧时刻（不是请求时刻） |
| 4 | `event` | **0 = 状态快照**（新增取值；1/2 含义不变） |
| 5 | `fault_id` | 有活动故障时填该故障编号；**无活动故障时填 0** |
| 6 | `active` | 当前活动故障位掩码，**这是权威值** |
| 7 | `value` | 该故障的观测量（STUCK = 最近结算块 span）；无故障时 0 |

**帧数规则**：每个活动故障一位一帧；`active == 0` 时发**恰好一帧** `fault_id=0, value=0`。
当前只登记了 STUCK，所以实际永远是**恰好一帧**。
将来多故障时，多帧携带的 `active` 相同（都等于同一时刻的掩码），上位机按"最后一帧的 active"落定即可。

### 1.4 类型码表（新增一行）

```
0x16  GET_DIAG   LEN=0   请求故障状态快照（设备回 ACK + 一帧 event=0 的 0x86）
```

## 2. 快照与实时事件的区别（这是最容易混淆的地方）

| 维度 | 实时事件 `event=1/2` | 状态快照 `event=0` |
|---|---|---|
| 触发 | 状态**跃变**时自动发 | 只在收到 `GET_DIAG` 时发 |
| 语义 | "刚刚发生了一次确认/恢复" | "此刻设备上还有哪些故障" |
| 可能丢吗 | **会**（队列满时） | 也会，但丢了可以再查一次 |
| 会不会重复 | 不会（`reported` 已置位就不再发） | 每次查询都发一帧，重复查询就重复回 |
| 对设备状态的影响 | 成功后更新 `reported` | **无**（只读） |
| 上位机怎么用 | 写进事件表、更新状态 | **覆盖**本地掩码，写一行"状态同步"，**不进事件表** |

**三条硬规则**（对应你的第 1/2/3 条）：
1. 快照**不补发**历史事件。查询一次只回一帧"现在"，中间发生过几次确认/恢复，快照里看不出来。
2. 快照**不得**让上位机产生"确认"或"恢复"的显示——所以它是 `event=0`，不是 `event=1/2` 的变体。
3. `active=0` 的快照必须发得出来（`fault_id=0`），否则上位机无法区分"没有故障"和"没收到应答"。

## 3. TX 队列失败后的状态机

### 3.1 把两件事拆开

现在 `app_fault_t` 只有一个 `active` 字段，把"设备是什么状态"和"上位机知不知道"混成了一个。
改造后拆成两个：

```c
typedef struct
{
  uint8_t  active;        /* 设备当前真实状态（来自 app_diag）        */
  uint8_t  reported;      /* 上位机已知状态（最后一次成功入队后的值）  */
  uint32_t last_try_ms;   /* 上次尝试发送的时刻（节流用）              */
  uint32_t retry_fail;    /* 连续失败次数（观测用，不上报）            */
  uint16_t value;         /* 最近一次状态对应的观测量（span）          */
} app_fault_t;
```

**不变式**：`active != reported` ⟺ "有一帧该发还没发出去"。

### 3.2 每样本只登记状态，不直接发帧

原来的 `app_fault_update()` 是"置位 + 立刻发"，失败就永久丢。改成两段：

```c
/* ① 每样本调：只登记真实状态，不产生任何副作用到发送层 */
void app_fault_set_state(app_fault_t *f, uint8_t fault_id, uint8_t is_active, uint16_t value);

/* ② 主循环调（每轮一次）：尝试把"没对齐的状态"发出去 */
uint8_t app_fault_service(app_fault_t *f, uint32_t now_ms, uint8_t tx_has_room,
                          app_fault_emit_fn emit, void *user);
```

`emit` 回调的返回值要改：**从 `void` 改成 `uint8_t`（1=入队成功）**。
这就是"不得把 `app_tx_write()` 的返回值直接丢弃"的落点。

### 3.3 三道闸门（防止每 10 ms 刷一帧）

```
① active == reported        → 直接返回（99.99% 的样本走这条）
② tx_has_room == 0          → 返回，不发。**在取 SEQ 之前就放弃，不烧序号**
③ now - last_try < 100 ms   → 返回（节流，避免队列一直满时每轮都试）
```

三闸门全过，才构造一帧、取 SEQ、入队。

- 闸门②由 `app_task` 计算并传入：
  `tx_has_room = (APP_TX_RING_SIZE - 1 - app_tx_pending()) >= PROTO_MAX_FRAME`
  —— 用最坏帧长做判断，宁可多等一轮，也不让 `emit_frame()` 白烧一个 SEQ。
- 闸门③的 100 ms 是**待确认参数**：它决定"队列恢复后最多等多久才重发"。

### 3.4 状态机（单故障视角）

```
                  ┌──────────────── 每样本 ────────────────┐
                  │ set_state(): active 可能变，reported 不动 │
                  └───────────────┬──────────────────────────┘
                                  v
                    ┌──────────────────────────┐
        active==reported ──是──►│   IDLE（不发）            │
                    │            └──────────────────────────┘
                    否
                    v
        ┌───────────────────────────────────────────┐
        │ PENDING（欠一帧）                          │
        │ 条件：队列有空间 且 距上次尝试 ≥ 100 ms      │
        │ 动作：event = active?CONFIRM:RECOVER        │
        │       入队成功 → reported = active → IDLE   │
        │       入队失败 → retry_fail++，留在 PENDING │
        └───────────────────────────────────────────┘
```

**PENDING 是"真状态"，不是"事件队列"**。这意味着：
- 队列满了三分钟，期间故障反复变化，恢复后只会补发**当前状态**的一帧，不会把中间 300 次边沿全发出去；
- 也永远不会发出"与当前状态矛盾"的帧。

## 4. 快速 确认 → 恢复 → 再确认 会怎样（逐条推演）

用 `R` 表示 reported，`A` 表示 active：

| 序列 | 队列 | 结果 | 上位机看到 |
|---|---|---|---|
| A:1 → A:0 → A:1（全程队列满） | 满 | R 始终 0；队列恢复后发 **1 帧 CONFIRM** | 一直是"有故障"，中间没恢复过 —— **状态对，边沿少了 2 个** |
| A:1（发成功，R=1）→ A:0（失败）→ A:1 | 中途满 | 第二次 A:1 时 `A==R`，不发任何帧 | 一直显示"有故障" —— **状态对，丢了恢复边沿** |
| A:1（成功，R=1）→ A:0（成功，R=0）→ A:1（成功，R=1） | 正常 | 3 帧依次发出 | 确认→恢复→确认，**完整** |
| A:1（失败）→ A:0（此时 A==R==0） | 满 | 不发任何帧 | 一直"无故障" —— **状态对**（确实没上报过确认，也就没有"恢复"可言） |

**结论**：`active/reported` 差分模型保证**永远不会发出错误事件**，但在队列阻塞期间**可能丢掉中间边沿**。
这是有意的取舍：可靠投递每一条边沿需要一个有界事件队列（8 槽 ≈ 40 B RAM + 更复杂的状态机），
而且在"链路断了 5 分钟"这种场景下，补发 300 条历史事件对操作员也没有意义。

> **需要你确认的点**：接受"状态一定对、边沿可能合并"，还是坚持"每条边沿都要投递"？
> 前者配合 `GET_DIAG` 已经够用；后者我需要在设计里加一个有界事件队列。

## 5. 快照与实时事件交错（你的第 7 条）

**问题**：如果快照在"收到请求时"就构造好、过一会儿才入队，它可能比一个更新的恢复事件更晚入队，
上位机按到达顺序处理，就会用旧快照覆盖新状态。

**解法（两条一起用）**：

1. **快照在入队那一刻才取状态**：只置标志，`app_fault_service()` 里现读 `active` 现组帧。
   所以快照的内容不可能早于排在它之前的任何帧。
2. **单队列 + 全局 SEQ**：ACK、快照、实时事件走同一个 `app_tx` 环、同一个帧序号，
   到达顺序 == 入队顺序 == 事件发生顺序。

**上位机规则**：`event=0` 时 **无条件**用 `active` 覆盖本地掩码（它是"截至这一帧"的权威值），
不做"比时间戳取新"这种判断——时间戳是设备毫秒计数，跨上电会回绕，靠它比较是坑。

推演：`active=1` 时查询 → 快照(1) 入队 → 随后恢复 → 事件(0) 入队
→ 上位机依次收到 1、0，最终 0，正确。
反过来若快照晚入队却携带旧值，就会得到 1，错误——所以第 1 条是硬约束。

## 10. 待你确认的 4 个点

1. **边沿合并能否接受**（§4）。接受 → 按本设计做；不接受 → 我加一个有界事件队列（8 槽），代价 +40 B RAM 与更复杂的状态机。
2. **节流间隔取 100 ms 行不行**。太小会在队列持续满时反复尝试（每次尝试要判空间，代价很小，但日志会多）；太大则恢复后要等更久。
3. **快照的 `fault_id=0` 是否合适**。另一种写法是 `fault_id` 固定填 1（STUCK）、靠 `active=0` 表示无故障；我倾向 0 = "无活动故障"，语义更直白。
4. **上位机连接成功后是否自动查一次**。自动查能立刻对齐；但会多发一帧命令 + 两帧应答。我倾向**自动查**。

确认后我再动手，并按"改 → 全量回归（C 892 + 上位机 66 + 界面冒烟）→ 板级 → 提交"的流程走。
