# 测试证据清单：Stage 1–4（按证据类型分类）

> 目的：Stage 1–4 的结论散在四份报告里，很容易被读成"全都是硬件实测"。
> 本文件把它们按**证据来源**重新归类，并把"哪些结论只能由哪一类证据支撑"写在最前面。
>
> 一句话原则：**PC 上跑通不等于板上跑通；注入故障造成的现象不等于真实故障造成的现象。**
> 混在一起写，就是夸大。

---

## 1. 三类证据的定义

| 类 | 名称 | 判定标准 | 能证明什么 | 不能证明什么 |
|---|---|---|---|---|
| **A** | PC 离机测试 | 不接板。编译器 / Python 在电脑上跑 | 纯逻辑正确性、协议两端字节一致性、界面数据通路 | 任何硬件行为（时序、电气、中断竞争） |
| **B** | 真板 + 真实信号 / 真实电气事件 | 板子在线，信号来自真实器件（电位器、电源轨），异常来自真实物理原因（错误波特率、自发噪声） | 整条链路在真实硬件上的行为 | 极端电气故障（除非真的制造出来） |
| **C** | 真板 + 人为注入 | 板子在线，但异常是被构造出来的 | 特定分支/恢复路径的可达性与反应时间 | 真实故障的**发生率**与**成因分布** |

C 类再细分三档，强度递减：

| 档 | 注入方式 | 例子 | 强度说明 |
|---|---|---|---|
| **C1** | 纯软件置标志，不碰硬件 | `adcinject` → `app_measure_on_error()` | 只证明"标志→恢复"这段代码通，**不证明真实 DMA 会这样出错** |
| **C2** | 软件手段制造**真实**硬件状态 | `AbortReceive` 后不回挂 → 真实 `RxState=READY`；停 DMA 攒字节 → 真实 ORE 置位 | 状态是硬件真的，但**成因不是现场会发生的** |
| **C3** | 脚本构造异常字节流 | 坏 CRC、LEN=255、半截帧、140 B 长命令 | 链路电气是真的，**异常内容是人为的** |

### 2.3 Stage 3 — UART + DMA + IDLE 异常（2026-11-03 08:58–09:01，COM6，Release `Code=20700`）

| 检查项 | 类 | 结论 | 证据 |
|---|---|---|---|
| CRC 错误 ×20 → `frame_err +20`，链路存活 | C3 | ✅ | `STAGE3_RAW.txt` |
| LEN 非法 41 / 255 / 200 → `frame_err +3`，无越界 | C3 | ✅ | 同上 |
| 半截帧 → **确定性吃掉后续 2 帧**（4/6 成功） | C3 | ⚠ 缺陷，已由加固 A 消除 | 见 2.4 |
| 未知 TYPE 0x99 → ACK `result=2`，`cmd_err +1` | C3 | ✅ | — |

| **FE / NE 风暴（错误波特率）** → `uart_err +144`、`rxf +0`、自动恢复 | **B** | ✅ 真实电气错误，不是构造的 | `ERRSRC fe=144 ne=0` |
| **ORE 注入** → `saw_ore=1`，链路不受影响 | **C2** | ✅ 但**未进中断**：DMA 读 DR 时顺带清了 ORE | `oreinject` 输出 |
| RX 环 256 B 溢出 | — | ❌ **NOT TESTED**（需主循环阻塞 > 22 ms） | 见 R7 |
| 真实 HAL 重挂失败 | — | ❌ **NOT TESTED** | **见 R1（必须保留）** |

> **ORE 那条要特别说清**：这是本项目最容易讲过头的结论。
> 我们确实让硬件置起了 ORE（`saw_ore=1` 是读 `USART1->SR` 得到的），
> 但重新挂接收后 DMA 取走 DR 的同时把 ORE 清了，**错误中断根本没机会执行**。
> 所以正确结论是"**本设计下 ORE 不会造成链路停摆**"，而不是"ORE 恢复路径已验证"。

## 3. 按类型汇总（谁支撑了哪部分结论）

| 类 | 数量 | 主要贡献 | 短板 |
|---|---|---|---|
| **A（PC）** | 3 组：Python 28 项、GUI 冒烟 1 次、C 单测 167 断言 | 逻辑正确性、协议两端一致、界面通路 | 完全不涉及硬件 |
| **B（真板真信号）** | 约 20 项：10 min 长跑、零点/满量程、HT 正反对照、扫掠 16 段、帧节拍 3503 点、FE 风暴、A5 边界、恢复耗时… | 链路的真实行为与真实电气异常 | 造不出"真实 DMA 电气故障""真实 HAL BUSY" |
| **C1（软件置标志）** | 20 次 `adcinject` | 恢复路径代码可达 | **不证明真实故障会被捕获** |
| **C2（造真实硬件状态）** | ORE 注入、`rxstop` ×12、B 组恢复 | 恢复机制与限速真实有效 | 成因不是现场成因 |
| **C3（构造字节流）** | 9 组异常帧 + A 组 6 项 + 长命令 | 解析器健壮性、帧边界 | 不含真实线路噪声 |

**一句话**：B 类撑起"能用"，A 类撑起"逻辑对"，C 类撑起"坏了能恢复"。
**没有一类能单独撑起"长期可靠"** —— 那要靠 §5 的 R3（8 小时长跑）。

## 4. 每阶段"能证明 / 不能证明"

| 阶段 | 能证明 | 不能证明 |
|---|---|---|
| 1 | 错误标志→主循环恢复→重新采样 这条路径通；恢复 < 5 ms；限速 1 s 有效；恢复不丢样 | 真实 DMA 会怎样出错；DeInit 失败时怎么办 |
| 2 | 换算与滤波实现正确；群延迟 40 ms；全量程单调无死区；时间戳无抖动 | 读数**绝对准确**（比例测量盲区）；INL/DNL |
| 3 | 解析器对坏帧/半帧/长帧的处理与整帧原子性；真实 FE 风暴可自愈 | RX 环溢出；真实 HAL 重挂失败 |
| 3 加固 | 半帧连锁已消除（3/3）；接收停摆可被 200 ms 内救回 | 启动本身失败时（`HAL_BUSY`）的表现 |
| 4 | 三个纯逻辑模块在真实源码上的行为 | 4 个 HAL 相关模块；ARMCC5 下的执行差异 |

| R13 | PC-Lint / Cppcheck / MISRA 未运行 | 低 | 未安装/未配置 | 无法声称"通过静态检查" | 装工具后跑一次，只报事实 |
| R14 | 阈值掉电不保存 | 低（设计限制） | 有意不做 EEPROM | 重启回默认 2400/3000 | 记录为限制，不算缺陷 |
| **R15** | **Stage 7C-2：TX 环真实满载后的重试** | **中** | 只有 C 单测模拟 `emit` 返回 0（`test_fault.c` "队列满不消耗 SEQ / 恢复后提交最新 active"）。**板上从未制造过真实环满**。环 1024 B、稳态 1744 B/s，单靠自然流量需 DMA 停摆约 0.6 s；**但可用「命令放大」在板级灌满**（`stat` 6 B 上行 → 254 B 回复，100 条/s ≈ 25.4 KB/s，约 74 ms 填满 1023 B），方案见 `docs/STAGE8_PLAN.md` §3.2，**尚未执行**（8A 现为可选，排在 8B 之后）（另见本文件 §5.2 的 TX 代码审查备注） | 真实满载时"不烧序号、恢复后自愈"只有推演，没有实测 | 按 `docs/STAGE8_PLAN.md` §3 执行 8A：每 10 ms 灌一条 `stat` 把环灌满 → 窗口内制造一次恢复边沿 → 停灌后核对「只提交 1 帧 / `rep` 拉平 / `retry_fail` 增量 0」。**不需要改 `APP_TX_RING_SIZE`，也不需要外部干扰** |
| **R16** | **Stage 7C-2：100 ms 重试节流** | 低 | C 单测覆盖边界（`app_fault_service` 的 `now - last_try >= 100`），**未做板级满载验证** | 真实满载时重试频率只有推演 | 同 R15，两者要一起测才有意义 |
| **R17** | **Stage 7C-2：多故障快照** | 低 | 仅白盒单测（手工置 `active=0x03`，断言 `fault_id=0 / value=0`）。固件目前只登记 `STUCK` 一种，生产路径走不到该分支 | 多故障并存时的快照格式没有真机证据 | 等第二种故障实现后一并上板；现在如实记为"仅单测" |
| **R18** | **Stage 7C-2：队列检查与写入的并发** | 低 | **代码审查通过**：`ACK`（`app_cmd_poll`）与 `FAULT`（`app_fault_service`）都在主循环顺序执行，**无 ISR 入队生产者**；`s_busy` 与 DMA 完成回调的竞争是既有设计，本轮未改动。**Stage 8 决策：保持代码审查证据，不升级为板级验证**（8A 灌满也不能证明该窗口） | 若将来把入队移进中断，"检查成功但写入失败"会重新出现 | 保持"入队只在主循环"这条约束；若破例，`reported` 的拉平必须改为以 `app_tx_write()` 返回值为准 |
| **R19** | **真实传感器诊断（断线 / 探头失效）** | 中 | **NOT TESTED**。手上只有电位器；"卡死"在电气上等价于"电位器不动"，但**不能声称验证了传感器失效** | 真实传感器失效可能不被 `STUCK` 检出（例如漂移到轨、周期性抖动） | 接真实传感器（或可编程信号源）后按 `STAGE7_FAULT_DIAG_DESIGN.md` §8 复测 |
| **R20** | **诊断 1h / 8h 长期运行** | 中 | **NOT TESTED**。Stage 7C-2 板级累计约 10 分钟（含轮询），未做长跑 | 诊断开启后的长期稳定性、计数溢出无从判断；误报只能看终点 `conf` 是否增长，**无法量化** | 按 `STAGE8_PLAN.md` §4：`SET_DIAG 1` 后原样跑 `soak.py`（1 h，通过后再 8 h），**结束后一次 `stat`**。只要求记录：**起点与终点 `conf`**、终点 `en / state / mask / rep / span`，以及 `soak.py` 的**全程采集统计**（帧率 / drops / seq8 缺口 / 整帧丢失 / 解析错误 / adc·uart·frm 错误 / BOOT / 重连）。**不要求记录 FAULT 帧数**——本轮不改 `soak.py`，也没有全程诊断打点 |
| **R21** | **GUI 按钮连接真实开发板** | 低 | **NOT TESTED**。界面联动是离屏冒烟（软件模拟）验的；真板路径走脚本（同一份 `protocol.py`，但没点过界面按钮） | 真机上勾选/查询按钮的实际闭环未验证 | 单独占用串口打开 GUI 连板，手动点"使能诊断 + 查询故障状态"各一次 |

> **R15–R21 的状态标注规则**：`UNIT PASS` = 只在 GCC/Python 单测里通过；
> `CODE REVIEW PASS` = 只有代码审查，没有运行证据；`NOT TESTED` = 完全没有。
> **任何一条都不得写成"板级 PASS"。**

### 5.1 两项保留风险的"当前正确说法"

面试/交付时如果要提这两条，按下面说，别升级也别淡化：
