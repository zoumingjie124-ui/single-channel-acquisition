## 2. App 层与 HAL 层的职责边界

### 2.1 先看代码实际长什么样（不看 README 的声明）

README 原来写的是"应用层不直接调 HAL，`app_measure` 除外"。**这句话不成立**。
把所有 `HAL_*` 调用点和 include 拉出来，真实情况是这样：

| 方向 | 位置 | 内容 | 性质 |
|---|---|---|---|
| **App → HAL** | `App/Src/app_measure.c:91` | `HAL_ADC_Start_DMA(&hadc1, ...)` | **设计允许**：它就是"ADC 采样隔离层" |
| | `App/Src/app_measure.c:138` | `HAL_GetTick()` | 同上（取时基） |
| | `App/Src/app_measure.c:159` | `ADC1_RecoverInit()`（`adc.c` 里的 HAL 复位） | 同上 |
| | `App/Src/app_tx.c:109` | `HAL_UART_Transmit_DMA(s_huart, ...)` | ⚠ **越层**：发送适配没下沉 |
| | `App/Src/app_task.c:423` | `HAL_GPIO_WritePin(LED_GPIO_Port, LED_Pin, ...)` | ⚠ **越层**：业务层直接点灯 |
| **HAL → App** | `Core/Src/adc.c:18,118,132,146` | `include "app_measure.h"`；三个回调调 `app_measure_on_half/cplt/error` | 回调就地对接 |
| | `Core/Src/usart.c:25-27,204,226,247` | `include app_config/app_cmd/app_tx`；回调调 `app_cmd_rx_isr` / `app_tx_on_cplt` / `app_tx_on_error` | 同上 |
| | `Core/Src/tim.c:17,87` | `app_task_tick_isr()` | 同上 |
| | `Core/Src/gpio.c:13,66` | `app_task_on_key()` | 同上 |
| **App → App** | `app_task.c:31` ↔ `app_cmd.c:13` | 互相 include 对方头文件 | 循环依赖（见 §2.5） |

结论一句话：**这个工程不是严格分层的，而是"上下双向接线"**。
`Core/` 负责硬件与中断入口，`App/` 负责业务；两边通过回调直接互调，中间没有注册表、没有函数指针表。
这样写的好处是路径短、看得见；代价是 `Core` 离开 `App` 就编不过，`App` 离开 `Core` 也编不过。

### 2.2 关于 `app_task.c` 调用 `HAL_GPIO_WritePin()` 的判定

**事实**（`App/Src/app_task.c:416-424`）：

```c
static void led_write(uint8_t on)
{
  if (s_led_last == on) { return; }
  s_led_last = on;
  HAL_GPIO_WritePin(LED_GPIO_Port, LED_Pin, (on != 0u) ? GPIO_PIN_RESET : GPIO_PIN_SET);
}
```

- `LED_GPIO_Port` / `LED_Pin` 来自 `main.h`（`GPIOC` / `GPIO_PIN_13`），
  所以 `app_task.c:22` 才要 `#include "main.h"`；
- **低电平点亮**这个板级事实也写在了应用层（`GPIO_PIN_RESET = 亮`）。

**这算不算问题：算结构问题，不算功能问题。** 具体四条影响：

| # | 影响 | 具体后果 |
|---|---|---|
| 1 | 可移植性 | 换一块 LED 接在别处、或改成高电平点亮的板子，要改**应用层业务代码**，而不是改 `gpio.c` |
| 2 | **可测性** | `app_task.c` 因此无法进 Stage 4 的 C 单测（需要 `stm32f1xx_hal.h` 才能编）。这正是 `STAGE4` §6.2 把 `app_task.c` 列为 NOT TESTED 的**直接原因之一** |
| 3 | 职责重复 | 极性 `RESET=亮` 在 `gpio.c` 初始化（`HAL_GPIO_WritePin(..., GPIO_PIN_SET)` 熄灭）和应用层各写一遍，两处必须同步改 |
| 4 | 与声明不符 | README 说"不直接调 HAL"，代码在调；文档与代码打架，比代码本身更伤 |

**风险等级：低。** 它不会让采样错、不会让帧错、不会有电气后果。属于"看得见的结构债"。

**最小改法（本轮不实施，等确认）**：

```c
/* Core/Src/gpio.c 追加 */
void led_set(uint8_t on)
{
  /* 板级事实集中在这里：PC13 低电平点亮 */
  HAL_GPIO_WritePin(LED_GPIO_Port, LED_Pin, (on != 0u) ? GPIO_PIN_RESET : GPIO_PIN_SET);
}
```

```c
/* App/Src/app_task.c 只改一行 */
- HAL_GPIO_WritePin(LED_GPIO_Port, LED_Pin, (on != 0u) ? GPIO_PIN_RESET : GPIO_PIN_SET);
+ led_set(on);
```

- 改完 `app_task.c` 不再需要 `main.h`（`LED_*` 宏是唯一用途），可以顺手去掉 `:22` 那行 include；
- 预计尺寸变化：**+8~16 B**（一次跨文件调用，ARMCC5 可能内联也可能不内联），需重编译确认；
- 成本不是改代码，而是**改完必须重烧 + 重跑一轮回归**（至少 Stage 1 的 30 s 采样率 + Stage 3 的 A 组），
  否则"为了好看动的刀"没有验证过，跟没改一样。

**为什么本轮不动**：任务书写了"不擅自重构"。这一刀收益是文档一致性，风险是碰了主循环里每秒调用上万次的路径。
要不要动，你定；动的话我按"改 → 重编译 → 重烧 → 重跑回归 → 单独提交"走一遍。

### 2.3 `app_tx.c` 直接调 `HAL_UART_Transmit_DMA()` —— 同一类问题，但性质不同

- 位置：`App/Src/app_tx.c:109`，头文件 `app_tx.h:24` 直接 `#include "stm32f1xx_hal.h"`；
- 它是**驱动适配代码**（环形队列 + 单帧串行），不是业务逻辑，越层程度比 LED 轻；
- 但它同样把 `UART_HandleTypeDef` 暴露到了 App 头文件里，这也是 `app_tx.c` 进不了 C 单测的原因。
- 将来若要收口，最小做法是 `usart_send_dma(const uint8_t*, uint16_t)` 放在 `usart.c`，
  `app_tx.c` 只留队列逻辑 —— **本轮不做**，同样等确认。

### 2.4 反方向：`Core/` 依赖 `App/` 是不是问题

`adc.c` / `usart.c` / `tim.c` / `gpio.c` 都 include 了 App 的头文件并直接调用 App 函数。
严格分层下这是"下层依赖上层"，不该出现；但在裸机 HAL 工程里它是最常见的写法：

| 好处 | 代价 |
|---|---|
| 回调路径最短，没有函数指针注册、没有空指针检查 | `Core` 与 `App` 互相依赖，任一目录单独拷走都编不过 |
| 编译期就能发现"回调没接上" | 想换一套应用逻辑，必须改 `Core` |
| 代码好读，面试时能一眼讲清数据流 | 无法把 `Core` 单独复用到另一个项目 |

**判定：不构成缺陷，是有意的取舍。** 本项目就一个产品、一套 App，收益大于代价。
README §2 已按这个事实改写，不再声称"严格分层"。

### 2.5 App 内部的循环依赖：`app_task` ↔ `app_cmd`

- `app_task.c:31` include `app_cmd.h`（要 `app_cmd_poll` / `app_cmd_init`）；
- `app_cmd.c:13` include `app_task.h`（要 `app_task_next_frame_seq()`，`:50` 用它给 ACK 编帧头）。

这构成头文件层面的循环。C 语言靠 include guard 能编过，但语义上不好：**"帧序号"是协议层的概念，
却挂在调度模块上**。将来若要收口，把它下放成 `proto_next_seq()`（`app_proto` 里一个 8 位计数器），
两边都只依赖 `app_proto.h`，环就断了。**本轮不做。**

### 2.6 边界判定小结

| 越界点 | 严重度 | 会不会影响功能/安全 | 建议 |
|---|---|---|---|
| `app_task.c` 调 `HAL_GPIO_WritePin` | 轻（结构债） | 不会 | 加 `led_set()`，**等确认**，改完必须重跑回归 |
| `app_tx.c` 调 `HAL_UART_Transmit_DMA` | 轻 | 不会 | 加 `usart_send_dma()`，**等确认** |
| `app_measure.c` 调 ADC HAL | 无（本就是隔离层） | 不会 | 保持 |
| `Core` 回调直调 App | 无（有意取舍） | 不会 | 保持，README 已如实描述 |
| `app_task` ↔ `app_cmd` 循环 include | 轻 | 不会 | 帧序号下放 `app_proto`，**等确认** |
| `app_task_uptime_ms()` 定义了没人调用 | 极轻（死接口） | 不会 | 可删可留；删掉省 4 B，不删也无害 |

> 但全工程没有任何调用点。以前清理过 `app_stats_t` 的死字段，这个属同类。
