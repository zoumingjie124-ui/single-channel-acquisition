## 2. 已通过的板级验证（只列真实执行过的）

设备：STM32F103C8T6 + CH340 USB-TTL，`115200 8N1`，PA1 ← 电位器。
原始日志：`docs/STAGE7C2_BOARD_RAW.txt`（脚本自动落盘，非手填）。

| # | 做了什么 | 结果 |
|---|---|---|
| 1 | 复位后立即 `GET_DIAG` | `ACK seq=46 (result=OK)` → `快照 seq=47`，`id=0 mask=0x00 value=0` —— **ACK 在前、快照紧随、SEQ 连续** |
| 2 | `SET_DIAG(1)` 后保持输入不动 | `ACK seq=199`，**3.02 s** 后确认帧 `seq=250`，`mask=0x01 value=8 mV`（8 mV 正是静置输入的块内峰峰值） |
| 3 | 有故障时 `GET_DIAG` | `ACK seq=39` → `快照 seq=40`，`id=STUCK mask=0x01 value=12` |
| 4 | **关闭串口**（模拟断线），设备继续运行 | 期间 `conf` 由 1 涨到 2 —— 说明**断线期间确实发生过"恢复→再次确认"**，事件帧丢了 |
| 5 | 重连后立刻 `GET_DIAG` | 快照如实返回 `mask=0x01`（当时窗口已过、设备已重判为卡死）。**没有改写成"同步成功"，原样记录** |
| 6 | 重连后**连续轮询** `GET_DIAG`（每 350 ms）并人手来回拧电位器 | **57 帧快照全部 `mask=0x00`** —— 断线期间发生的恢复被快照正确同步 |
| 7 | 停手静置后 `stat` | `conf=4`，设备自行重新判定卡死；`mask=1 rep=1`（`rep` 与 `mask` 拉平，说明提交成功） |
| 8 | 全程计数器 | `drops / adc_err / uart_err / frame_err` 全 0，解析错误 0；首段 **915 帧、SEQ 异常 0 个**（跨 255→0 回绕仍连续） |

**这 8 项是唯一可以称为"板级验证"的内容。** 它们证明的是：
查询/应答的时序与字段正确、真实故障能触发确认、断线后快照能给出当前真相、
关闭诊断不会伪造恢复、全局序号不被快照打乱。

### 5.1 设计层面仍存在的取舍（不是缺陷，但要知道）

1. **边沿可能被合并**：队列阻塞期间发生的多次确认/恢复，恢复后只提交当时的状态。
   丢的是"历史事件"，不是"当前状态"——由 GET_DIAG 兜底。已批准。
2. **`reported` 只代表入队成功**：`app_tx_write()` 成功 ≠ DMA 发完 ≠ 对端收到。
   所以重连后仍必须查快照，快照与事件不能互相替代。已写入 `PROTOCOL.md` §4.8.1。
3. **关闭诊断不清故障状态**：`diag off` 后 `mask` 仍会保留到下次上电，
   这是"关闭诊断 ≠ 故障恢复"的必然结果，快照也如实返回该状态。
