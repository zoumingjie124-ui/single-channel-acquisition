## 2. 打点

**479 条**，覆盖 60 s – 28740 s，每分钟一条。
479 而不是 480，是 `soak.py` 的循环逻辑决定的：`while` 开头先判 `elapsed >= total` 再决定是否打点，

最小值 **5705**、最大值 **6002**、均值 **6000.23**；**477/478 落在 6000–6002**。

唯一偏低区间 `[7260s]`：**ΔSAMPLE = 5705**（比 6000 少 **295**、比 6001 少 **296**）、**ΔSTAT = 57**（少 3）；
该分钟的 `drops / frame_err / seq8 缺口 / 整帧丢失 / 解析错` **全部为 0**。

**不能写成链路丢帧**：若真丢 296 帧，8 位序号缺口应为 `296 mod 256 = ` **40**，实测 **0**；整帧丢失也是 0。
这是一次**计数台阶**，不是通信丢帧。

分段偏移拟合：前段 **100.014031 样本/s（140.3 ppm）**、后段 **100.014084 样本/s（140.8 ppm）**，
两段斜率一致；两条直线外推到 7260 s 处相差 **−295.5 个样本 ≈ −2.95 s**。

**结论：观察到一次计数台阶（≈ −2.95 s），判定为「主机侧时钟前跳（NTP 校时）」。**
依据：① Windows 事件日志 `2026-11-05 01:28:27` 系统时间被 `svchost.exe` 前跳 **+2950 ms**；
② 该事件落在 `7200→7260 s` 区间内（elapsed ≈ 7206 s）；③ H11 推演——若为设备停顿而 uptime 照走，
残差应约 4.07 s，实测 1.12 s；④ `soak.py` 计时用墙钟 `time.time()`（L65/L76/L164），
墙钟前跳会使打点提前触发、`dur` 同步拉长。
**不写"已证实"**：因日志未保存逐帧 STAT 的 `t_ms` 原文，无法直接从帧流核对该分钟的设备侧时长，
故维持四项证据的合取推断。
`台阶前后 STAT 运行时间是否连续` **无法检查**（原始帧未保存）——该项保持 **OPEN**。
详见 `STAGE8B_REPORT` §8.3.1 / §8.3.2。

区间内 `5705` 相对 `57 s × 100 Hz = 5700` 的 **+5**，属**打点边界量化**，**不用来解释漂移**。

总账：8 小时按 140 ppm 漂移应得 **+403** 个样本，减去台阶 **−295**，得 **+108**；
实测累计 `2874109 − 2874000 = +109`，差 1 个样本，落在打点边界量化范围内。

### 3.1 H11 正式计算

```
T0  uptime0 =   166805 ms  @ 2026-11-04 23:26:07.236   （reset 后基线）
T1  uptime  = 29130168 ms  @ 2026-11-05 07:28:49.479   （终点 STAT）
Δuptime = 28963363 ms
Δwall   = 28962243 ms
差值    = +1120 ms
偏差    = |Δuptime − Δwall| / Δwall = 0.0039 %   门槛 < 0.1 % → PASS
```

> **精度声明**：终点 `uptime` 取自 1 Hz 的 STAT 帧，存在约 **±1 s** 的量化误差，
> 对应 ±0.0035%，与本处 1120 ms 的残差同量级。因此本项只声称"时基偏差 < 0.01% 量级"，
> **不宣称得到精确到毫秒的 HSE 偏差**。
>
> **对 0.0039 % 的分解（原"原因未查"已撤回）**：对累计 SAMPLE 做分段偏移拟合，**7260 s 台阶前后斜率均约 140 ppm**，
> 台阶约 **−295 个样本（≈2.95 s）**；`140.5 ppm（拟合值）× 28962 s ≈ 4.07 s`，减去台阶 ≈ **1.12 s**，与实测 `+1120 ms` 吻合。
> 取整说明：按 **140 ppm** 取整为 `4.05 s`（差 0.02 s），差别仅来自 ppm 取整；本节统一取 **4.07 s**。
> 即 **H11 的 0.0039 % = "140 ppm 真实速率差" ＋ "一次 −2.95 s 台阶"**；
> **1 小时的 Y / Y2 / X2 三轮 0.0142 % 才是 140 ppm 的直接体现**（11:24 那轮 0.0077 %）。
> 因此 **H11 不得跨轮次比较**：本轮的 0.0039 % 比 1 小时轮"好看"，是台阶抵消的结果，不是时基更准。
> **台阶侧别：主机侧时钟前跳（NTP 校时）**——依据事件日志 +2950 ms、时间对齐、H11 推演与墙钟计时基准
> （`STAGE8B_REPORT` §8.3.1 / §8.3.2）；**未写"已证实"**，`STAT 运行时间连续性` 仍为 **OPEN**。

## 4. 序号检测能力的边界（必读）

本轮 `frame_gap = 0`、`seq8_gap = 0`，按统一口径表述：

> 在当前 8 位序号检测能力范围内，未检出可分辨的序号缺口（`frame_gap` 与 `seq8_gap` 均受同一限制）。

边界说明：
- 两个指标都基于 **8 位**序号，差值按 `(x − exp) & 0xFF` 计算；
- 因此**单次连续丢失恰为 256 的整数倍**帧时，增量会被算成 0，无法识别；
- 该盲区是**每次间歇**层面的，不是累计层面（分两次各丢 128 帧仍会计出 256）；
- 由此，"未检出"**不等于**"绝对零丢失"，只能说"在可分辨精度内为零"。
- **打点层面的旁证（§2.1）**：若发生 256 帧的整倍丢失，某一分钟的 ΔSAMPLE 会比该分钟应有值低约 256 的整倍
  （标准 60 s 区间 ≈**5744**）。本轮唯一偏低区间是**台阶**而非丢帧（依据：`seq8 缺口` 与 `整帧丢失` 均为 0；
  若真丢 296 帧，序号缺口应为 `296 mod 256 = 40`），**未见无法解释的 256 整数倍缺口**；
  但若丢失恰好落在某个完整 60 s 区间内，Δt 与 ΔSTAT 都不变、序号也不留痕，**仍然不可识别**——所以本节措辞不放宽。

另需注意：`seq8 缺口` 与 `整帧丢失` 对同一个丢失的 SAMPLE 帧会**各计一次**，二者不可相加。
本轮两者同为 0，不涉及该问题；若将来出现非零，必须按 `frame_gap` 与 `seq8_gap` 分开解释。

## 6. 证据等级

- **板级实测**，**统计级证据**（soak 的统计 + 每分钟打点 + 终点 STAT/DIAG 文本行）。
- **不是字节级全量验证**：原始二进制帧流未落盘，无法事后重放或逐帧复算。
- 覆盖范围：1 条链路、1 台主机、1 个构建（Code=22468）、诊断关闭状态、8 小时尺度。
- **已知限制（计时基准）**：`soak.py` 用**墙钟** `time.time()` 计时（L65/L76/L164），
  长跑中遇到 NTP 校时会在打点里留下**计数台阶**。本轮实际出现一次（**+2950 ms**，见 §2.1）。
  **本脚本未修改**；建议长跑前**关闭 Windows 自动校时**，或跑完后对照 `Time-Service` / `Kernel-General`
  事件日志再解读打点。
