## H1. TX 环真实满载后的重试

### H1.1 要证明什么

设备端"故障状态"与"已提交状态"分离后，在**发送环真的满**时：

1. 不构造帧、**不消耗全局 SEQ**；
2. `reported` 不前进（`stat` 文本行的 `rep=` 与 `mask=` 保持不等）；
3. 100 ms 节流生效（不是每个 10 ms 采样周期都试一次）；
4. 环恢复后**只提交一次**，且内容是当时的 `active`，不是历史边沿。

### H1.2 两条路线，都需要你批准

| 路线 | 做法 | 代价 / 风险 |
|---|---|---|
| **A. 改配置**（推荐先做） | 临时把 `APP_TX_RING_SIZE` 从 1024 改到 **256**，重编译烧录 → 环在几百毫秒内就能灌满 | **属于改固件**，必须你点头；测完必须改回 1024 重烧，并在报告里注明"测的是 256 B 环的等价行为" |
| B. 制造真实停摆 | 让 DMA 持续发不出去（如外部强干扰、总线被占） | 不可控、可能真的丢数据；无法保证复现 |

> **为什么是 256 而不是 64**：`stat` 文本行实测约 90–100 字符（最坏情况近 190），
> 64 B 甚至 128 B 的环都装不下一行 `stat` → 整行被丢弃并计 `txd=`，
> 而 `DIAG`/`STAT` 文本行正是本测试**唯一的状态观测通道**。环太小会把观测通道自己堵死，
> 测出来的现象无法解释。256 B 既够小（~150 ms 停摆即满）、又保证文本行写得进去。
> 附带影响：`APP_FAULT_RETRY_MIN_MS=100` 的注释里明确写了"环改小需重算"，测完必须还原并复核该注释。

> 路线 A 只能证明"环满 → 不烧号 → 恢复后补发"这条**逻辑**在真实中断/主循环时序下成立，
> **不等于**证明了 1024 B 环在真实电气故障下的行为。报告里必须这么写。

### H1.3 步骤（按路线 A）

1. 改 `APP_TX_RING_SIZE` → 256，编译（确认 0E0W），烧录；
2. 打开串口，`SET_DIAG 1` 使能诊断，保持输入不动直到出现确认帧；
3. **制造拥塞**：连续快速发 `GET_STAT`（每 10 ms 一条）把发送环灌满，持续 3 s；
   同时用 `diag_watch.py` 抓帧；
4. 观察 `stat` 文本行的 `DIAG ... mask=1 rep=0`（应出现 `rep` 落后于 `mask`）；
   注意：拥塞期间文本行本身也可能被丢弃，所以**以拥塞解除后的第一行 `stat` 为准**；
5. 停止灌命令，等 1 s，再 `stat`：应看到 `rep=1`，且期间**只多出 1 帧 FAULT**；
6. 记录：SEQ 是否出现跳号（不该有）、FAULT 帧总数、`rep` 追上 `mask` 的时间。

### H1.4 通过标准

| 判据 | 期望 |
|---|---|
| 拥塞期间的 SEQ | **连续无跳号**（跳号 = 白烧了序号，即缺陷） |
| 拥塞期间 FAULT 帧数 | 0（环满，发不出去） |
| 恢复后 FAULT 帧数 | **恰好 1 帧**，`event=1 active=1` |
| `rep` 追平 `mask` | 停止灌命令后 ≤ 200 ms |
| 采样率 / 丢点 | 仍 100.0x Hz、`drops=0`（拥塞不该影响采集） |

## H2. 真实传感器诊断

### H2.1 要证明什么

`STUCK`（连续 3 个 1 s 块 `max−min < 50 mV`）在**真实传感器**上：
不误报（正常波动不触发）、能报（真卡死能触发）。
以及——**当前硬件根本测不了"断线"**，这一条要作为结论写出来，而不是含糊过去。

### H2.2 硬件现状（重要）

- PA1 配的是 `GPIO_MODE_ANALOG`，**无内部上下拉**。悬空读数不确定 → 没有可预期特征值 → 无法做断线判据。
- 要可靠检测断线，需要加**偏置电阻**（100 kΩ 级，把悬空拉到已知电平）。**这是硬件改动，需你批准**。
- 在此之前，可行的只有"观察实验"：把 PA1 从电位器上摘下，**空置 30 s**，记录 `raw_mv` 的分布
  （是否漂到轨、是否大幅抖动、是否落在 0 或 4095 附近）。**这个实验不改任何代码**，只记录现象。

### H2.3 分两步

| 步 | 内容 | 需要什么 |
|---|---|---|
| H2-a | **悬空 30 s 观察实验**：记录 `raw_mv` min/max/均值/是否贴轨，据此判断"断线"是否有可判据的特征 | 只要拔掉 PA1 的线（断电后操作） |
| H2-b | 接**真实传感器**（或可编程信号源）做误报/漏报统计 | 传感器或信号源；若要做断线检测还需偏置电阻 |

### H2.4 通过标准（H2-b）

| 判据 | 期望 |
|---|---|
| 正常波动 10 min | FAULT 确认帧 **0**（`STUCK_DELTA_MV=50 mV` 是否合适，就看这一条） |
| 真卡死（传感器输出被固定） | 3 s 内确认，`value` = 实测块内峰峰值 |
| 恢复 | 连续 2 个干净块后发恢复帧 |

> `STUCK_DELTA_MV` 目前仍是**待确定**值（依据只有电位器静置实测峰峰 8–12 mV）。
> 真实传感器接上后必须重新标定，不能沿用 50 mV 当结论。

### H2.5 现状

**未开始。** H2-a 只需要你拔一根线；H2-b 需要硬件。

## H3. 诊断开启 1h / 8h 长期运行

### H3.1 要证明什么

诊断**开启**状态下连续跑，不扰动采集链路、不误报、不慢性失效：
采样率、`drops`、`frame_err`、`adc_err`、`uart_err`、SEQ 缺口、`BOOT` 帧、重连次数全 0；
`conf` / `rep` 不异常增长；FAULT 帧数符合"边沿数"而不是"每样本一帧"。

### H3.2 前置条件（缺一不可）

1. **关掉睡眠/休眠/USB 选择性暂停**——命令在 `docs/SOAK_PLAN.md` §9.1，**测完必须还原**（§9.2）。
   原因见 `TEST_REPORT` §17.3：睡眠会让数据"假干净"。
2. `soak.py` 与 GUI / `diag_watch.py` **不能同时占同一个串口**。
3. 输入保持在一个**不会自行跳变**的状态（电位器固定），否则会不断产生确认/恢复边沿，干扰判读。

### H3.3 步骤

1. 先跑 **1 h**：`SET_DIAG 1` → 确认出现 1 帧确认 → 保持不动 → `soak.py 60 COM6`；
2. 中途每 5 min 记一次 `stat` 的 `DIAG` 行（`en/state/conf/span/mask/rep`）；
3. 1 h 通过后再起 **8 h**（`soak.py 480 COM6`），每 30 min 打点；
4. 记录格式沿用 `docs/SOAK_PLAN.md` 的表 A/表 B 与 H1–H12 门槛。

### H3.4 通过标准

沿用 `SOAK_PLAN.md` 的 **H1–H12**（100.00±0.10 Hz、`drops=0`、`BOOT=0`、时基偏差 <0.1% 等），另加：

| 附加判据 | 期望 |
|---|---|
| FAULT 帧总数 | 等于实际边沿数（固定输入下应 **= 1 帧确认**，不应持续增长） |
| `conf` 增量 | 0（输入不动就不该有新确认） |
| `rep` | 恒等于 `mask`（无拥塞就必须拉平） |
| 8 h 结束的 `uptime` | 与窗口时长偏差 <0.1% |

### H3.5 现状

**未开始。** 另有一个**工具缺口**：现有 `diag_watch.py` 是秒级窗口（默认 20 s），
`soak.py` 只统计 SAMPLE/STAT、**不单独统计 FAULT 帧数**。
要做 H3 的"FAULT 帧总数"判据，需要给 `soak.py` 加一个小计数（属**新工具改动，待你批准**）。
在批准前，H3 只能用 `stat` 文本行手工打点，判据会弱一档。
