## 4. 被阻塞的验证：卡死触发 / 恢复 / 重复触发（测试 #3/#4/#5）

### 4.1 阻塞一：正式固件运行时无处使能诊断（非脚本遗漏，是固件设计）

全仓证据：
- `app_diag_set_enable()` **仅在 `fw_tests/test_diag.c`（PC 单测）被调用**；固件运行时从不调用。
- `enable` 只被 `app_diag_init()`（置默认 0）与 `set_enable` 写；`app_task.c:475` 只调 `app_diag_init`。
- `APP_DIAG_STUCK_ENABLE_DEFAULT = 0`；`APP_DEBUG_INJECT = 0`（正式版不编入注入命令）。
- 协议 V5 命令集（`0x10`–`0x14` + 文本 `help/stat/thr/led/reset`）**无诊断使能命令**；STAT 帧无 diag 字段 → **卡死状态经串口不可观测**（属 7C）。

因此：在当前正式固件上，**不开调试器、不改代码，就无法开启卡死检测，也无法经串口看到它的状态。**
按指示"不得为测试修改协议/代码、无法使能先报告"，本轮**未改代码、未改协议**。

### 4.2 阻塞二：需要人工物理操作电位器

#3（保持不动看触发）、#4（转动看恢复）、#5（再固定看重复触发）都要求**用手保持/缓慢转动/停住电位器**
并与触发/恢复时刻对齐记录。执行方为软件代理，**无物理执行器**，此三步必须有人在台面操作。

### 4.3 结论

#3/#4/#5 = **未验证（阻塞）**。不存在任何"已触发/已恢复"的板级证据；**不要**把上位机无故障显示当作检测失败（协议本无上报）。

## 5. 人工台面补测步骤（供完成 #3/#4/#5，不改代码）

唯一不改代码的使能/观测路径 = **调试器直写 + 监视 `s_ctx.diag`**（STLink 已连接）：

1. Keil 连板（不 halt 主循环，用 Live Watch / Memory 窗口）。
2. 使能：写 `s_ctx.diag.enable = 1`（并确认 `blk_started` 由下一样本自然开块）。
3. 监视字段：`state`、`confirm_cnt`、`stuck_blocks`、`clean_blocks`、`last_span`、`last_change_ms`。
4. 台面动作与记录（记**实际时刻**，不只 PASS/FAIL）：
   - 电位器保持不动 → 记录 state 进入 ACTIVE 的时刻（预期约 3 s，块边界附近会有 ±1 s 抖动）；
   - 缓慢转动 → 记录回到 CLEAR 的时刻（预期约 2 s 干净块）；
   - 再次固定 → 记录第二次 ACTIVE（`confirm_cnt` +1）。
5. 串口侧并行跑 `host/tools/hw_soak.cmd COM6 <分钟>` 记录 raw_mv/filt_mv 与计数器，与调试器时刻对齐。
6. 阈值提醒：`STUCK_DELTA_MV=50 mV` 是**实验值**，接真实传感器前必须按噪声/正常变化范围重新标定。
