## 5. 归因分析（H7/H8/H12）

### 5.1 设备侧证据：全部为零

| 计数器 | 值 | 含义 |
|---|---|---|
| `drops` | 0 | 采样环没溢出，一个采样点都没丢 |
| `adc_err` / `uart_err` / `rx_err` / `frame_err` | 0 / 0 / 0 / 0 | 设备端未记录任何错误 |
| `txd=` | **0 B** | **发送环从未满**，`app_tx_write` 一次都没丢字节 |
| `BOOT` | 0 | 中途没有复位 |
| 链路中断 | 0 | 串口没有断开重连 |

`txd=0` 只能证明**入队没丢**：`app_tx_write()` 没有因为环满而丢弃过任何一帧。
它**不能**证明"线上传输正确"——字节是否正确发出、是否完整到达主机，这一层固件没有任何计数可查。

### 5.2 观测事实：缺口与解析错误成对出现

- `seq8 缺口 = 45` 与 `整帧丢失 = 45` **必然相等**：两者是同一批丢失帧的两种算法
  （样本级 / 帧级），不是两条独立证据。它们的相等只能说明**丢失的全部是 SAMPLE 帧，
  没有 STAT 帧丢失**，不能反推"丢的是整帧而非帧内错位"。
- `解析错误 = 30`：解析器遇到过**无法完成的帧**并重新同步。日志只能说明
  "**字节流被破坏**"，**无法区分**是丢了字节、还是字节被改坏，
  **也无法定位**发生在设备引脚、USB 链路还是主机驱动。
- 时间分布：59 个打点中 **28 个**带缺口，且**全部落在 240–2460 s** 这一段内
  （窗口内 38 个打点里 28 个有缺口；窗口外 21 个打点全为 0）。窗口内每次增量只有
  **1 / 2 / 3 帧**，没有出现更大的成块丢失。28 个"缺口有增量"的打点与 28 个
  "解析错有增量"的打点在时刻上重合——**这与"该处发生了字节级破坏"一致**，
  但**破坏发生在哪一段、以何种方式发生仍未确定**（设备引脚 / USB 链路 / 主机驱动都不能排除）。详见 §5.3。

### 5.3 缺口的时间分布（复盘后新增，修正了初版归因）

统计每个 60 s 打点窗口内的增量（原始表见 `SOAK_60MIN_20261104.txt`）：

打点是**累计值**：`[ 240s]` 那一行报的是 `(180, 240]` 这一分钟内的增量，
`[2460s]` 那一行报的是 `(2400, 2460]`。因此"有增量的打点"只能把事件定位到**一分钟区间**，
不能定位到某一秒。

| 区间 | 打点 | 现象 |
|---|---|---|
| 0 – 180 s（11:24:12–11:27:12） | 60 / 120 / 180，共 3 个 | **完全干净**（0 缺口 / 0 解析错） |
| **起点在 11:27:12–11:28:12 之间，终点在 12:04:12–12:05:12 之间**<br>（对应打点 240 … 2460，覆盖 180–2460 s） | 共 38 个 | 其中 **28 个有缺口**；每次 1–3 帧；累计 45 帧 / 30 次解析错 |
| 2460 s 之后（12:05:12–12:24:12） | **2520 … 3540，共 18 个**；3540–3600 s **无打点**，只有合计段 | **重新完全干净**（0 缺口 / 0 解析错） |

也就是说：不是"全程均匀丢一点"，而是**一段有界窗口**——首个有增量的打点是 240 s
（事件落在 180–240 s 之间），末个是 2460 s（事件落在 2400–2460 s 之间），
故窗口长度在 **36–38 分钟**之间；打点粒度 60 s，**无法再精确**。两端都是干净的。

末段"无打点"这一点有独立佐证：**3540 s 那条打点的累计值（45 / 45 / 30）与合计段完全相同**，
说明 `(3540, 3600]` 这最后一分钟没有新增缺口或解析错误——不是"没记"，是"确实没发生"。

### 5.4 归因（初版结论已作废）

**初版写的"测试期间本机并发执行大量文件读取导致"不成立。**

依据（会话记录，非系统级）：本次静态审查的**第一次文件读取发生在 12:10:08**；
在此之前，本会话最近一次工具调用是 **11:24:26**（即开跑后 14 秒内的日志核验与记录写入）。
也就是说 **11:24:26 → 12:10:08 之间有 45 分 42 秒本会话零调用**，
而丢失窗口（11:27:12–12:05:12）完整落在这段静默期内。

**这条证据的边界**：它只能证明**本会话**在那段时间没有发起读写，
**不能**代表整台机器空闲——系统更新、杀毒扫描、其它程序、以及人工操作都不在记录范围内。
因此准确表述是：**"本会话在丢失窗口内没有活动"，而不是"主机在丢失窗口内空闲"**。

排查过的系统侧证据（均不支持"主机 CPU 被抢占"）：

| 检查 | 结果 |
|---|---|
| System 日志（11:20–12:30）的 USB / 串口 / PnP / 磁盘错误与警告 | **无任何记录** |
| Defender 扫描 | 上一次快速扫描是 11-03 19:25，**不在窗口内** |
| 任务计划日志 | 未启用，读不到 |

剩下的候选：

| 候选 | 支持 | 反对 |
|---|---|---|
| A. 主机 USB 接收缓冲偶发溢出（进程被短暂挂起 / 端口被 hub 节电） | 缺口与解析错误成对出现；设备侧 `txd=0`、`drops=0` | 未找到对应的系统事件；且"开始/结束"都太干脆 |
| B. 设备侧待发缓冲被覆盖 / 越界（非"供数不及"） | 若 `s_stage` 或环内内容被错误改写，主机侧会收到破坏的字节流 | **`uart_err=0` 只覆盖 RX，排除不了发送侧**；但固件没有 TX 侧完整性计数。<br>**注意：串口"发送慢"只会拉长字节间隔，不会改坏字节**，所以"供数不及导致移位错误"这个机制不成立，已从候选中删除。<br>另外，缓冲被覆盖通常与负载/时序相关，与"有界窗口"**不太像，但不能排除**——若冲突是否发生取决于时钟相位对齐，理论上也可能出现有界窗口（**推演，未验证**） |
| C. 物理层（USB 线 / hub / 接触） | 窗口有界，符合"某个外部扰动持续一段时间后消失"；本机 CH340 的端口路径为 `LOCATION=1-2.1.3`，**说明接在 hub 之后**（经一级以上的 hub 级联），hub 供电/线材/接触都可能引入这类有界扰动 | 无直接证据；System 日志没有对应的 USB 告警 |

**结论：只能确定丢在"设备发送环之后、上位机解析器之前"，具体归属未定论。**
本轮**不记为通过**，也不把任何候选写成既成事实。

#### 8.3.2 `soak.py` 的计时基准（代码核对）

`host/tools/soak.py` 共 195 行，SHA-256 `26771dd161ea34224a9133f3ca717bdbf2ff0ba8596fcb4c6e19aaa4af58c9ab`。
**全文计时只用墙钟 `time.time()`，没有 `time.monotonic()`，也没有 `time.perf_counter()`**：

| 行号 | 代码 | 作用 |
|---|---|---|
| **L65** | `t0 = time.time()` | 计时起点 |

### 9.3 H11 与 8B-2 的差异（本轮最重要的解释）

- 8B-2（`en=0`）报 **0.0039 %**，本轮（`en=1`）报 **0.0141 %**，相差约 100 ppm。
- 原因不是设备变差：8B-2 窗口内有一次主机 **NTP +2950 ms** 前跳，把 `Δwall` 拉长 2.95 s，
  `4.07 s − 2.95 s ≈ 1.12 s`；本轮 `NoSync` 且事件日志无阶跃，测到的 **141 ppm 才是真实量级**，
  与 8B-2 分段拟合的 140 ppm 完全吻合。
- 结论：**H11 只能逐轮对照"是否 < 0.1 %"，不得跨轮次比较绝对值**；8B-2 的 0.0039 % 是表观值。

### 9.5 `conf` 的口径（容易误读，必须写清）

`reset`（23:10:36）把 `conf` 清零，而当时模块**已经处于 ACTIVE**；此后 8 小时输入一直卡死，
没有发生 CLEAR→CONFIRM，所以 `conf` 全程为 **0**（增量 0）。

**要特别记一笔：起跑时（§9.1 / 当天晚间的记录）按"`conf` 会 0→1"预期写过，那句预期是错的。**

**源码依据（已逐行核对，不是推断）**：

| 事实 | 出处 |
|---|---|
| `conf` = `confirm_cnt`，语义"进入 ACTIVE 的次数" | `App/Inc/app_diag.h:53`（字段注释） |
| `confirm_cnt` **只**在 `CLEAR / CONFIRMING` 分支、且 `stuck_blocks` 达到阈值时 `++` | `App/Src/app_diag.c:114–122`，自增语句在 **L120** |
| 已处于 `ACTIVE` 时再来偏死块，**只做"取消恢复"、不重新确认**（故不累加） | `App/Src/app_diag.c:129–134`，注释原文"已确认过的状态：偏死块只是'取消恢复'，不需要再确认" |

所以本轮 `reset` 把 `conf` 清零时模块已是 ACTIVE，之后 8 h 输入一直卡死、从未回到 CLEAR，
**`conf` 必然全程 0**——这与"没有误报"是同一件事，不是漏计。X2 是 `conf 1→1`（增量 0）。
**两者结论相同（无异常增量），但绝对值不可混用**——引用 R20 时必须注明本轮 `conf=0` 的成因。

**`blk` 的含义（已查源码，非未解读）**：`blk` 取的是 `app_diag_block_samples()`，
即**当前尚未结算的 1 s 统计块里已计入的样本数**（100 Hz ⇒ 取值 0–100），块结算后清零。

| 事实 | 出处 |
|---|---|
| DIAG 文本行 `blk=%u` 实参为 `app_diag_block_samples(&s_ctx.diag)` | `App/Src/app_task.c:338`（格式串）、**L343**（实参） |
| `blk_samples` = "本块已计入的样本数（用于判断块是否可评估）" | `App/Inc/app_diag.h:44` |
| 块结算后 `blk_samples = 0`，等下一个样本开新块 | `App/Src/app_diag.c:88` |

因此 T0 `blk=73`、终点 `blk=88`、二次读取 `blk=49` **非单调是设计使然**（每 1 s 归零重计），
**与设备健康状况无关，不能当判据**；它只说明"取样时刻落在一个块的什么位置"。
