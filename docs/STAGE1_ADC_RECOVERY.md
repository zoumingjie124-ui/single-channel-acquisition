# 阶段一：ADC 故障恢复验证

> 版本：v5.1.11 基础上（固件正式版仍为 `Code=20700`）
> 日期：2026-11-02
> 硬件：STM32F103C8T6 (Blue Pill) + USB-TTL(CH340) · COM5 · 115200 8N1
> 结论：**恢复链路可跑通，恢复耗时 2.4–7.2 ms，10 次恢复丢样 0（计数取整内）**

---

## 0. 结论速览

| 检查点 | 结论 | 证据 |
|---|---|---|
| 1. DMA 错误是否被记录 | ✅ | 注入后 `adc_err` +1，文本 STAT 的 `adc=` 同步可见 |
| 2. ISR 是否只置标志 | ✅ | 代码结构 + 实测恢复耗时 4 ms 量级（无长时间占中断） |
| 3. 主循环是否执行 DeInit/Init | ✅ | 每次注入都出现 `[rec] adc restarted` |
| 4. 重启后是否恢复采样 | ✅ | 恢复后 30 s 实测 **100.03 Hz / 3001 帧** |
| 5. 是否产生重复/无效样本 | ⚠️ **部分** | 帧数精确：10 次恢复期间样本数 2032 / 理论 2032.6，**没有多出任何一帧**；但「旧值顶替新值」这类在静态输入下无法与噪声区分 |
| 6. 失败后是否有重试机制 | ✅ | 1 s 内注 5 次 → 只恢复 2 次，间隔 **998 ms** |
| 7. 计数是否正确 | ✅ | `adc_err` +N、`rec_ok` +N、`rec_fail` 0 |
| 8. 是否影响 TIM3 节拍 | ✅ | 恢复后采样率仍 100.03 Hz，`seq8` 缺口 0 |

---

## 1. 方法与边界（必须先说清）

**这是"路径注入"，不是真实电气故障。**

注入命令 `adcinject` 只做一件事：调用 `app_measure_on_error()`，等价于"DMA 错误中断里
那一行 `s_recover_req = 1`"。之后的 DeInit → Init → 校准 → Start_DMA 全部由主循环
按原逻辑执行。

它验证的是：**恢复流程被打断后能不能重新跑起来、代价多大**。
它**不能**证明：真实 DMA 电气故障（TE/溢出）下的恢复行为——那种故障在正常接线下
无法人为制造，本项目也没有做电气注入。

另外两条口径：

- `seq8` 只统计"已处理样本"，恢复期间没采到的样本**不会**产生缺口，
  所以**不能拿 `seq8` 判断丢点**，必须看"样本计数 vs 运行时间"；
- `SAMPLE.t_ms` 是"主循环处理该样本的时刻"，不是 ADC 转换时刻，
  所以恢复造成的空档在 `t_ms` 上也看不出来（本次实测全程严格 10 ms）。

## 2. 实测数据

### 2.1 单次注入

```
基线: adc_err=0 drop=0 n=847
注入命令响应  : 1 次 OK inject
固件回显      : adc_err=1 rec_ok=0 rec_fail=0      ← 回显早于恢复，故 rec_ok 仍为 0
恢复日志      : restarted=1  failed=0
adc_err 增量  : +1
drops   增量  : +0
采样率(30s)   : 100.03 Hz  (3001 帧)
seq8 缺口     : 0
RESULT: PASS
```

### 2.2 恢复耗时（回显 → 恢复完成）

连续注入 5 次（每次间隔 1.2 s 避开限速窗口）：

| 次序 | 命令回显 | 恢复完成 | 恢复本身 |
|---|---:|---:|---:|
| #1 | 5.4 ms | 2.4 ms | **2.4 ms** |
| #2 | 5.0 ms | 2.5 ms | **2.5 ms** |
| #3 | 4.9 ms | 2.5 ms | **2.5 ms** |
| #4 | 4.7 ms | 7.2 ms | **7.2 ms** |
| #5 | 4.8 ms | 4.2 ms | **4.2 ms** |

平均 **3.8 ms**，最大 **7.2 ms** —— 均小于一个采样周期（10 ms），因此**不丢采样**。

> "命令回显"那 5 ms 是主循环调度延迟（样本批处理 + 发送队列），不属于恢复成本。

### 2.3 丢样核对（10 次注入，累计计数法）

```
设备运行时间增量 : 20326 ms
样本计数增量     : 2032   (理论 2032.6)
差值             : -1     → 处于取整误差内
drops            : 0 -> 0
adc_err          : 7 -> 17   (+10)
```

结论：**10 次恢复，可测丢样 0（≤1 个，属计数取整）**。

### 2.4 限速（1 秒内连注 5 次）

```
注入时刻(ms): [0, 202, 403, 605, 807]
恢复时刻(ms): [7, 1005]
恢复次数    : 2 / 注入 5 次
恢复间隔(ms): [998]        ← 与 APP_ADC_RECOVER_INTERVAL_MS = 1000 一致
限速判定    : PASS
```

首次错误立即恢复（`s_try_started == 0` 的特例），其后 1 秒一次；
窗口内其余 3 次请求被合并进同一个标志，**没有打成忙循环**（期间 STAT 仍按 1 Hz 发出）。

## 3. 代码改动（最小、默认不生效）

| 文件 | 改动 | 是否进 Release |
|---|---|---|
| `App/Inc/app_config.h` | 新增 `APP_DEBUG_INJECT`，默认 **0u** | 否（默认 0，代码不参与编译） |
| `App/Src/app_task.c` | 新增文本命令 `adcinject`，整段包在 `#if (APP_DEBUG_INJECT != 0u)` 里 | 否 |

编译尺寸对照：

| 配置 | Code | 说明 |
|---|---:|---|
| `APP_DEBUG_INJECT = 0` | **20700** | 与改动前**逐字节一致**（RO 996 / RW 108 / ZI 4916） |
| `APP_DEBUG_INJECT = 1` | 20808 | +108 字节，仅测试用 |

测试结束后已把开关改回 0、重新编译并烧录，**当前板上是正式版固件**（实测 2 s 收到 200 帧 = 100.0 Hz）。

## 4. 尚未验证（诚实清单）

| 项 | 为什么没做 | 后续怎么补 |
|---|---|---|
| 真实 DMA 电气故障下的恢复 | 正常接线无法人为制造 TE/溢出；不做电气注入 | 只能靠长时间运行中出现 `adc_err > 0` 的真实样本（阶段五） |
| `DeInit/Init` 失败路径（`recover_fail`） | 正常硬件下不会失败，需编译桩 | 可另做一个"宏替换为 return 0"的实验构建，单独验证 |
| 恢复后首个样本是否被旧值顶替 | 已排除「多推一帧」（10 次恢复 0 多余帧）；但输入是 1531 mV 静态直流、噪声 ±5 mV，旧值与相邻正常样本在数值上不可分辨 | 需**动态信号**（斜坡/正弦）才能判：输入变化时旧值会明显落后于相邻样本 |
| 失败上限与降级策略 | 属设计取舍，未定 | 需先决定：持续失败是否要告警/停机 |
| 8 小时稳定性 | 未做 | 阶段五 |

## 5. 复现步骤

```bat
:: 1) 打开注入开关并烧录
::    App/Inc/app_config.h: #define APP_DEBUG_INJECT 1u
UV4.exe -r DataAcq.uvprojx -j0 -o build.log
UV4.exe -f DataAcq.uvprojx -j0 -o flash.log

:: 2) 单次注入 + 30 s 复核
python host\tools\adcrec.py COM5

:: 3) 连注验证限速
python host\tools\adcrec.py COM5 --burst

:: 4) 测完把开关改回 0，重新编译并烧录
```

预期输出见第 2 节；若回 `ERR unknown command: adcinject`，说明开关没打开或没重烧。
